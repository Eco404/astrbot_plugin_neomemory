# 显式旧节点依据协议的模型验证

## 结论

`extraction.v7 / extraction-prompt.v29`能够让模型声明实际使用的旧节点，并由程序保存输入快照的精确内容版本。gpt-6-luna的三窗连续链已经提交这种来源关系，说明能力可用；但它将正文中的两项具体限制缩为“此前两项规定”，使新事件独立注入时无法自足。因此本次只支持显式来源能力的局部有效性，**不支持将v29直接认定为整体质量优于v27，也不建议仅凭本次结果替换默认**。

gpt-5.6-luna的v29原实验在首窗引用不一致时停止。独立显式恢复在一次纠正后提交首窗，但第二窗再次出现引用不一致，且被拒候选混合了两次独立经历。原失败及恢复失败均保留；不能将显式续跑描述成原实验或生产后台的自动恢复成功。

## 方法和输入

`scripts/probe_extraction_basis.py`在读取输出前冻结一份独立三窗合成材料、两个模型、v27/v29及系统提示词。场景包括结束的修复经历、九天后另一场独立展示，以及展示的后续补充；第二窗通过指代引用第一窗明确的馆内查阅和禁止闪光规定。材料不来自私人会话。

每个分支使用自己实际提交的SQLite状态准备下一窗，首个生成、解析或提交失败即停止，不补理想前态。原计划最多12次窗口调用，实际尝试10窗并提交9窗；gpt-5.6-luna的v29后两窗未执行。

| 模型与提示词 | 原实验尝试/提交 | 主要观察 |
| --- | --- | --- |
| gpt-6-luna / v27 | 3/3 | 独立展示另建，后续继续同一展示；正文展开旧限制，但新事件没有旧节点版本依据 |
| gpt-6-luna / v29 | 3/3 | 独立展示另建并声明旧依据，后续继承展示旧版和限制原子；正文把具体限制缩为指代 |
| gpt-5.6-luna / v27 | 3/3 | 将独立展示更新到原修复事件，之后继续更新混合事件 |
| gpt-5.6-luna / v29 | 1/0 | local_ref与关系端点不一致，unknown_local_reference，链停止 |

原脚本把HTTP hooks及SDK重试设置安装在注册provider上，但结构化输出由adapter创建独立owned provider，因此原报告中的`http_requests=0`无效。能确认的是10次adapter调用；实际HTTP数量和传输重试未测，不能声称零HTTP或已排除传输重试。本报告保留原始结果文件并明确这一测量缺口。

## 语义和存储核对

gpt-6-luna v29第二窗的新展示事件使用两个实际输入的旧节点作为base；提交后版本依据对应原限制原子和修复事件的第一版。第三窗更新仍保留展示ID，程序自动继承其第一版，并保存模型明确声明的限制原子第一版。当前窗口直接来源与旧节点依据分开存储，没有把旧原文伪装为当前窗口直接引用。

对应v27第二窗也展开旧限制，但其新事件没有继承旧节点版本，第三窗只能继承这个已缺失历史基线的新事件。v7补足的是这条可追溯表达能力，不能由合法ID推断模型引用的内容一定充分、必要或正确。

正文完整性存在明确取舍：v27新事件写出了两项具体规定，v29第二、三窗仅写“此前两项规定”。规定仍在其他节点及来源链中，不能说整个数据库已经遗忘；但普通召回不会仅因base_versions存在而自动注入所有依据，所以只注入该事件时，读者无法知道两项规定是什么。本次没有执行真实向量召回或回答生成，不能进一步宣称最终回答已经错误。

两版gpt-6-luna都把“另一种延续”和后续说明组织为人格先误解、对方再澄清的过程，这一解释比来源更强。gpt-5.6-luna v27把独立活动合入同一事件；v29被拒候选也有同类合并。单次短链不能将这些错误归因于新增base字段，也不能认为引用能力自动修复了事件身份。

实现核对确认：v7要求显式base_node_ids列表，短引用按节点种类解码，事务限定为当前known_nodes，并使用准备快照版本。自身旧版自动继承；旧版本协议仍可显式运行。同文确认不为了补来源制造新正文版本，历史未记载的依据不会在升级时补造。工程验证与细节见主题依赖一致性报告及对应测试，不以这些检查替代模型事实审阅。

## 独立显式恢复

`scripts/probe_extraction_basis_recovery.py`先冻结原失败请求、候选、检查结果的摘要和调用上限，再复制失败臂真实source.db与memory.db。首窗重新准备的请求与原请求逐项相同，原库没有已提交批次；后续输入只使用纠正后实际提交的状态。

调用方法为生产ProviderAdapter、schema、引用转换和ExtractionService提交，纠正反馈复用生产生成器；这是评估脚本显式启动，不经过后台任务调度器。首窗最多3次纠正，后续两窗各最多一次生成并在失败时停止，HTTP总上限5。脚本在owned结构化provider上安装HTTP hook，SDK max_retries=0、宿主request_max_retries=1，修改仅限测试进程。

实际结果：

- 首窗第一次显式纠正使关系端点与local_ref一致，成功提交；两项规定及人格已有感受保留。
- 第二窗生成再次把coverage中的事件引用写成与local_ref不一致的形式，schema以unknown_local_reference拒绝；未提交，第三窗未执行。
- 第二窗未提交候选明确列出旧限制原子并展开规定，但把独立展示合入原修复事件。它只能作为被拒候选的质量观察，不计作已完成的v7连续链。
- 共2次adapter调用、2次HTTP请求，约28.48秒；其中1次为显式纠正、1次为新窗口生成。原实验的失败及结果文件未改写。

## 采用建议与后续验证

保留v29为显式候选，先验证“内容依据可追溯”与“正文可独立使用”同时成立。版本依据用于解释来源，不能代替正文应保留的必要条件；应以通用职责澄清和新独立留出材料验证，而不是为本场景补专用句式。

引用一致性继续通过已有有界纠正路径验证，不手工替换引用或放松schema。事件身份与条件保真分别评价：完整连续链、跨模型实际前态和最终注入证据齐备后，再判断默认采用。允许低影响瑕疵不等于把具体限制缺失或不同经历合并视为来源能力的收益。

私有运行材料位于`data/evaluations/extraction-basis-20261118/`与`data/evaluations/extraction-basis-recovery-20261118/`。其中原实验保留冻结manifest及所有失败，恢复目录保存副本、逐次请求/候选/事务结果和真实HTTP计数。本项不涉及实机部署、私人样本调整或平台消息发送。
