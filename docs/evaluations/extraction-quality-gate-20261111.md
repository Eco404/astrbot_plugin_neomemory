# 抽取质量候选与独立合成评估

工程版本：`f682283`。本地宿主基线为 AstrBot 4.29.3，Python 使用 Conda astrbot。生产仍为 `extraction-prompt.v7` / `extraction.v2`；`extraction-prompt.v8` / `extraction.v3` 是显式选择的候选，未部署到实机。

当前成果是可执行的声明一致性门禁、独立上下文来源存储和可复核的模型对照。新协议尚未满足默认升级的质量证据要求，不能据此声称实机发现的全部语义问题已解决。

## 独立输入与请求边界

固定材料是 `scripts/quality_gate_cases.py` 中8组全新虚构对话和合成人格。种子节点/画像由有真实来源记录的手写合成候选建立，不消耗模型请求；每个对照版本使用独立数据库、同样语义输入及来源短引用。

输入与审阅要求在请求前写入 manifest，夹具 SHA256 为 `04ac496f55fe9c5b511cd5e5cde1f79d9840f01a0b54f38680bb03b320d815c0`。未读取私人会话、实机产物或现用人格来制作夹具、调整规则或提示词。参考项目和适用边界记录在 ADR-0027。

通过真实 AstrBot ProviderAdapter 调用 `gpt-6-luna`；主对照8组×2版本，每组每版本最多一次HTTP，SDK重试0、宿主尝试1，无自动内容纠正。共16次HTTP：

- v7：7/8通过 schema、引用和事务提交；提议场景出现非法情绪标签 `hope`，被拒绝且未提交。其原始正文并未写成用户已经同意，不能把枚举失败当作事实归因错误。
- v8：7/8通过；最后一组画像场景收到503 `system_cpu_overloaded`，没有候选。这是服务失败，无法评价语义。
- 对503做一次独立补测，保留原失败；语义输入、系统提示词和审阅要求一致，增加1次HTTP。返回合法候选并提交，但没有画像输出。没有为取得非空画像再请求模型。

合计17次HTTP。两次运行的清单分别保存，不能将补测覆盖原来的7/8统计。最终 `f682283` 代码又在全新临时库中回放了所有已返回原始候选，新增网络调用0：15份提交、同一份非法标签候选仍拒绝，503仍标为没有输出。所有冻结系统提示词与最终代码逐字相同；回放不能独立证明模型的重复运行稳定性。

## 正文审阅

逐项审阅来源、种子基线、原始输出与规范化正文；没有目标产物或者只生成了其中部分事实时，未覆盖的能力标为 `not_evaluable`。合法 no_change 是正常选择，不能当作该类正文质量通过。

| 场景 | v7 | v8 |
| --- | --- | --- |
| 条件、否定、转述不确定性 | 保留验收前提、尚未报名、故障未查明 | 同样保留；声明与两项原子正文相容 |
| 用户/人格/第三方主体 | 只生成用户考试节点，主体正确 | 同样仅有用户考试节点；人格写开场白和第三方维修的节点归因仍无产物可测 |
| 另一时间同类经历 | 新建第二次课程；旧课精确日期来自已有节点，跨节点推导依赖未记录 | 新建第二次课程，直接来源支持其表述 |
| 同一事件后续完成 | 更新R-42原节点，保留送修过程、当前已修好取回 | 同样更新，same_event/completed与来源相容 |
| 提议后对方询问 | 非法情绪标签拒绝；未提交原文没有虚构接受 | 已提交关系保留未决定、询问时长及提议状态 |
| 明确接受但尚未执行 | 原子正确；关系输出为空，关系能力无法评价 | 事件planned、关系accepted，确认指向本人来源，保留第一次尚未进行 |
| 单次行为与人格猜测 | no_change，未观察到错误画像写入 | 同样no_change，不代表画像生成已经验证 |
| 明确新稳定偏好并继承旧画像 | 正确更新画像，保留陶艺及周日安排 | 初次503；补测只生成正确原子，未更新画像，画像及继承生成未验证 |

**新候选仍有引证分类问题。** 主体场景中，v8关系正文提到“准备了半年的经历”，但半年时长只在 `context_source_ids` 的s1，直接来源只有没有时长的s4。结合全部窗口能支持内容，不能据此认为直接引文充分。新增字段让缺口更容易看见，并未自动解决引证完整性。

v7另一经历的新节点还引用了既有节点中的精确日期，但当前协议没有新节点→其他节点版本的推导依赖声明。这是已知跨节点来源边界，不把已知上下文中的事实误判成凭空编造，也不推测补出未记录的依赖。

关系的纯主观感受仍允许自由表达，本次没有将主观期待逐句要求用户确认。语义声明只用于审阅，不加入被动召回，也没有增加额外生成请求。

## 成本与采用结论

| 指标 | v7 | v8 |
| --- | --- | --- |
| 主对照平均提示词正文 UTF-8 字节 | 20435.875 | 25647.875 |
| 主对照平均实际HTTP JSON请求体字节 | 21778.375 | 27280.375 |
| 8份返回候选的输入token总量 | 42011 | 51779（包含一次503补测） |
| 8份返回候选的输出token总量 | 2906 | 3302（包含一次503补测） |
| 8份返回候选原文总字节 | 4932 | 6203（包含一次503补测） |

输入token按Provider报告的 `input_other + input_cached` 计量，不能因v7命中缓存就把缓存部分从输入量删去。v8每个系统提示词增加5212字节，实际请求体增加5502字节；本样本输入token约增加23.3%。这是有用的成本边界，尚无足够证据证明这些成本换来了稳定质量提升。

v7返回候选耗时中位13.172秒；v8主对照7份返回候选中位13.360秒，加入补测后8份中位11.919秒。单模型、每场景一次且网络/缓存条件不同，不能宣称v8更快。

**采用结论：保留v7生产默认，v8仅隔离评估。** 当前不重新清理实机、不重构现用数据、不修改宿主输入截断行为。工程门禁和来源存储可独立合入，但语义质量未达到默认提示词升级的证据要求。

后续优化顺序：

1. 对直接来源与辅助上下文的分界做通用改进，检验每项新增事实是否都有直接引文；同时研究跨节点版本依赖，不能把所有窗口来源自动提升为直接证据。
2. 用新的独立材料验证明确稳定偏好的画像漏建及连续修正，并分别报告节点和画像产物；沿用轻量标签/短描述，不据本次遗漏强制所有消息生成画像。
3. 补充能实际产出人格动作、第三方动作和多用户来源的独立回放；缺少产物的本轮样本不算这些能力通过。
4. 对提示词增量做更小的对照、增加模型与重复运行，评估事实保留、选择性记忆、来源充分性和成本后再决定默认升级。新增生产LLM调用仍需单独决策。

现有工程问题已有修复和回归，本轮没有必须由用户立即选择的产品分歧。后续若需要改变选择性记忆、画像结构或生产调用次数，再提交具体取舍；不能用结构通过率替代这些决策。
