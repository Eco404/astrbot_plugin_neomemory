# 多话题候选融合独立评估

## 结论

新冻结的真实向量对照证实，全局最高相似度排序会让一个高分话题挤掉其他话题的正确旧节点。在默认总量30、近期10的条件下，既有`extraction-context.v2`补回了5种查询组合中的少数话题目标，未新增本次预标的无关语义候选。它应进入真实后台连续验证，不能继续笼统表述为“只有固定向量收益”。

唯一新探索的RRF方案也补回目标，但每个案例多引入2—6个无关语义候选，没有超过v2的目标收益，因此不建议接入生产。这里的判断基于相对收益及代价，允许少量瑕疵，不是要求候选零噪声。

本项没有修改生产候选选择或默认值，没有调用生成模型，也没有测试后续模型是否会正确新建或更新。

## 参考及冻结方案

先阅读[新建与更新研究](../research/event-create-update-balance.md)及[逐查询覆盖对照](context-coverage-20261117.md)，再核对本地Graphiti提交`5c27edfa8d3e0f49b2571bcebb4261bcc89ee037`（Apache-2.0）的`graphiti_core/search/search_utils.py::rrf`。该实现对每路排名累加`1 / (零基排名 + rank_const)`，默认`rank_const=1`。来源：[固定版本实现](https://github.com/getzep/graphiti/blob/5c27edfa8d3e0f49b2571bcebb4261bcc89ee037/graphiti_core/search/search_utils.py#L1786)。本地快照不代表已检查最新维护状态。

本探针独立实现该排名公式，借鉴多路融合设计，没有复制宿主集成或业务逻辑。Graphiti的多路检索方式不等同NeoMemory的多条消息，不能将其效果直接迁移；相似消息也可能放大同一话题。

三个分支共享完全相同的真实向量：

- **v1**：生产选择器，全局最大相似度排序，保留10个近期节点后填满30项。
- **v2**：已有显式覆盖候选，每查询保留一个高于既有0.35门限的代表，去重后全局补足；没有调整门限。
- **RRF探针**：每查询保留top30，按上述公式融合；精确重复查询去重，保留相同近期10，再按融合分数补满30；没有增加新的相似度门限或权重。

所有规则、文本、目标和代码hash在请求前写入manifest，没有根据输出筛选算法、修改场景、调参或补跑。RRF仅存在于`scripts/probe_context_fusion.py`，不是新的生产context版本。该原型一次加载全部测试向量，尚未实现生产的分页有界内存接口，不能直接替换生产函数。

## 材料与调用

52个独立合成节点：32条相近但不同的帆船维修记录、护照补交照片与手摇织机木梭修复两个少数话题、8条无关背景、10条近期记录。帆船组有意构造同一高分话题的竞争压力，其中白鹭号为特定旧事件，其余船只不属于同一次维修。少数话题使用自然续谈而非照抄旧正文。

8种查询组合覆盖双话题、三话题、主话题同义重复、精确重复、闲聊、无关提问、相似但独立的新经历，以及必要近期背景。目标节点和话题组在运行前标注；当前主话题的其他船只视为“不同经历干扰”，不直接等同无关或错误合并。近期10项是共同固定成本，不计入额外语义候选噪声。

Embedding模型为`@cf/baai/bge-m3`，61个去重文本、1024维，4次真实HTTP，约5.99秒，SDK无重试、0次LLM。全部案例复用同批向量，分支数不增加Embedding请求。未读取私人会话，也没有把旧实验素材改写为新留出。

证据：`data/evaluations/context-fusion-20261117/`，包含清单、真实向量、每条查询的完整排名/分数、三分支选中集合与体积。manifest SHA-256为`4556001d2bc588e17ed5676d85e56f6f8e203cffa9ea45d1f79217ce4503070b`。

分开统计：6类主要场景（双/三话题、闲聊、无关提问、独立新经历、近期背景）合计10个目标位置，v1为6/10，v2与RRF均10/10；2个重复控制组（主话题同义重复、精确重复）合计5个位置，v1为2/5，v2与RRF均5/5。汇总是8/15与15/15，但主要场景也共享52个节点，不能视作15个独立样本或普遍召回率。所有分支总量30、唯一性、近期10前缀均满足要求。

双话题中，护照旧节点是其查询的第一名，余弦约0.735；白鹭号为主话题第一名，约0.869，其他船只约0.81。全局排序让19条其他船只填满剩余名额，护照目标虽然是自己话题最相关节点仍未入选。v2用护照目标替换一条其他船只；三话题中同样补回木梭目标（其查询第一名约0.776）。这直接支持“逐查询覆盖减少跨话题分数竞争”这一机制。

RRF还将财务报销、照片备份、猫寄养等节点带入语义名额，因为它们在某路排名较前或在多路中累计得分。只使用相对名次无法判断每路第二、第三名是否真正相关；在本组输入中，额外噪声没有换来更多目标。

短句和无关提问下v2集合不变，但原因是它们的最高匹配恰好已属于近期固定名额：闲聊最高为已处理邮件的近期节点，约0.603；彩票问题最高为早餐记录，约0.441。**这不能证明0.35门限识别了无关内容。** 结合旧实验的一例弱相关项，v2仍可能被无关问题占位，只是本次没有额外挤占。

相似新经历案例没有把任何旧帆船列为正确更新目标；它只检查同窗护照续谈是否被挤掉。各分支出现旧船只候选是用于区分背景，并不证明模型会把新船只错误合并。新建/更新判断必须在后续真实后台链中单独审阅。

v1正文UTF-8合计约3790—3816字节，v2约3717—3790字节（新经历案例3784），RRF约3295—3559字节。RRF较短主要因无关条目正文短，不能据此称为上下文利用优化；这些数值不包含完整提示词、ID或schema，也不是被动召回预算。

## 工程与采用边界

固定正交向量只检查RRF的总30、近期10、精确查询去重和少数话题代表是否能保留；检查通过，脚本编译通过。真实Embedding结果与这些确定性检查分开报告。没有运行全插件测试、事务链、冷缓存大空间或模型回答质量验证；探针没有更改产品代码。

按用户接受小瑕疵、重视总体实用收益的标准，本次支持优先验证并考虑采用既有v2，而不是开发新的RRF生产路径。旧v2报告的一例噪声仍有效，本次覆盖收益也应同时计入；不能因轻微噪声拒绝全部收益，也不能因15/15目标位置命中忽略错误事件合并风险。

建议在后续后台连续链保持总量30/近期10，分别记录正确旧节点可见性、实际新建/更新/不变和不相关候选。先确认模型能够利用新增目标并区分不同事件，再确定生产默认；不为本组数据更改门限或写专用话题规则。

实际模型对新增候选的利用检查已独立记录在[四格事务对照](context-fusion-apply-20261117.md)。该后续使用相同已见检索材料，不合并成新的检索留出集，也不改变本报告的0次LLM口径。
