# 画像职责与候选覆盖组合链评估

## 结论

独立四格对照使用真实向量检索、候选准备、短引用还原和数据库提交。12个计划窗口中实际尝试8个，6个提交；两个分支在首窗输出非法情绪枚举后按冻结规则停止。不能从这份不完整的四格对照推断组合方案稳定优于基线。

其中有两项可定位的结果：基线在第三窗未选入相关旧事件，随后把重复信息新建为事件；组合分支能建立原本缺失的画像、保留未来变更生效前的当前安排，第三窗返回无变化。但组合首窗也无增量地重写一个旧原子。因此既支持改善画像独立职责和观察候选可见性，也保留无意义更新风险，不以节点少作为采用依据。

## 冻结设计与边界

脚本：`scripts/probe_memory_duties_context.py`。四臂为v26/context.v1、v27/context.v1、v26/context.v2、v27/context.v2；每臂三个连续窗口，使用同一合成人格及同一组独立来源。每个分支有独立原始库和记忆库，下一窗只使用自己真正提交的前态，失败后停止，不替换为理想前态。

初始14个已有节点包含职业及长期阅读习惯原子，但没有画像；本批本人明确重述这些信息，使“长期已存不等于画像已表达”有直接来源可验证。另有两个持续项目、同类但独立的旧项目以及近期无关事件。

- 首窗：两个项目各自推进；本人重述工作和稳定阅读习惯。
- 第二窗：已有项目获许可但尚未执行，另一个新项目独立开始；阅读安排下月变更，本月仍按旧安排；新增持续爱好；人格表达自己的不同爱好。
- 第三窗：明确重复既有状态，没有新进展。

候选上限固定6，是缩小名额的压力配置，不是生产默认30。每窗真实执行 `select_context_ids → ExtractionService.prepare → ExtractionReferences → Provider → decode → apply`；不是直接把所有旧节点塞给模型。保存全部候选ID、实际输入、原始输出、提交前后状态和回执。

采用AstrBot原生Responses Provider、`gpt-6-luna`，text模式；真实Cloudflare Embedding。SDK与宿主网络重试关闭，不启用内容纠正，首次结构或提交失败即停止该分支。此为语义及候选路径对照，不是MaintenanceEngine后台恢复验收；有界纠错另见[恢复评估](candidate-recovery-20261117.md)。

LLM预算12次HTTP，Embedding预算60次；实际8次LLM、16次Embedding HTTP，约143.13秒。虽共用缓存数据库，分支的空间ID独立，因此没有跨分支向量复用；同一分支内部复用旧节点向量。缓存键包含模型指纹、空间、文本哈希、节点ID与版本，不会将相同ID/版本但不同正文的向量混用。

运行前冻结场景、模板、实现哈希、参数和语义判据。第一次启动因脚本将JSON读回的list与原tuple直接比较，在Provider创建及任何HTTP之前停止；仅修复清单序列化比较，在新目录重新冻结，原证据未覆盖。没有根据模型结果修改场景或重跑。

运行后候选模块的函数说明文字进一步澄清：相似度门限不保证语义相关。最终文件哈希因此与运行冻结值不同；逐字还原这两处docstring措辞后，源码SHA-256与冻结值完全一致，执行代码没有变化。本报告引用实际冻结版本和保存请求，不将不同文件哈希混写成同一运行证据。

执行清单SHA-256：`1b901c7cfcc35acc46f610f77e1efcde7c0ed0691aea9185d57b6333de2c52f1`。证据目录为被Git忽略的 `data/evaluations/memory-duties-context-20261117-run/`；前述零HTTP启动记录位于不带`-run`的目录。

## 逐臂结果

| 分支 | 提交／尝试 | 观察 |
| --- | ---: | --- |
| v26 + context.v1 | 3/3 | 首窗两个旧事件正确更新，但未建画像；第二窗阅读原子未入候选而新建；第三窗南馆事件未入候选，将重复的明日操作新建为事件 |
| v27 + context.v1 | 0/1 | 画像候选包含工作、阅读频率与持续时间；关系使用非法`relief`，整窗拒绝。此外关系仅引Agent来源，不能把画像候选记为已存 |
| v26 + context.v2 | 0/1 | 两个旧事件更新候选合理，但画像为空，关系同样使用非法`relief`；整窗拒绝 |
| v27 + context.v2 | 3/3 | 画像初建、后续新增爱好及当前/未来安排保留；旧项目更新与新项目分离正确；第三窗无变化。首窗旧习惯原子被无增量重写 |

首窗四臂实际选入同样的旧节点集合。因此首窗画像差异不是候选可见性造成，也不能因单次生成就完全归因于提示词。两失败臂没有后续观测，无法完整分离第二、三窗中的提示词、候选策略及不同生成前态影响。

## 语义审阅

人工逐窗对照固定来源、完整旧节点、真正被选中的候选和提交后内容；没有用关键词命中代替判断，没有将schema失败的草稿改成可提交结果。

**画像职责。** 基线首窗的习惯原子已进入候选，本人也明确重述，但画像为空；第二窗新增长期爱好仍未建立画像。v27两臂首窗都提出了有依据的画像，只有组合臂实际提交。组合第二窗保留职业、持续时间、本月周日与下月周六的区别，并新增持续三年的邮戳爱好。人格折纸没有进入用户画像。这个结果支持职责分离有局部价值，不证明多模型普遍改善。

**事件身份与候选。** 两个完成的分支都能将原项目进展更新在原ID，并为新项目另建事件。基线第三窗旧项目不在候选中，重复事实被新建，这是独立材料中“候选缺失后重复新建”的具体路径证据。组合第三窗两个项目与习惯均可见，返回no_change，但其前态与基线已经不同，不能仅据此量化context.v2效果。

**无增量更新。** 组合首窗旧习惯原子的职业、阅读对象、频率和持续时长没有新增或改变，只被换句式却提交更新，内容版本由1变2。这不是无副作用润色，会影响强度基准和覆盖有效性，必须计为不足。不能用后续画像完整或第三窗no_change抵消该问题。

**状态与情绪。** 两个成功分支均保留许可、执行、公开发布之间的区别，未把未执行写成完成；组合保留旧导线准备信息，基线首窗省略了这一已有细节。用户担忧归属正确并保留，未将人格自身爱好或释然归给用户。对重要情绪的判断仅限这条链，不代表所有旧情绪更新已可靠。

四个隔离记忆库完整性与外键检查通过；提交批次数分别3、0、0、3，失败臂没有半份画像落库。直接应用链不测平台消息、任务租约恢复、真实关系长链或并发压力。

## 采用判断

本项不单独支持将context.v2或组合方案设为生产默认。画像模块还须结合其独立多模型对照判断；候选策略需同时证实遗漏减少及噪声不过量，不能为修复这条链的漏选定向调整。

下一步继续以独立材料检查：已存长期事实但画像为空时的初建、无信息增量时禁止内容重写、多话题的必要旧节点可见性，以及低相关短句是否占用名额。保持当前事件身份规则，不通过简单提高更新比例解决碎片问题。

## 工程交付复核

本报告所在提交以`4ac3be7`为父版本，交付画像职责模块、显式v27/context.v2入口、三个独立探针及相关工程测试；生产默认保持v26/context.v1，未部署或改写实机数据。画像、检索及组合实验合计31次生成模型HTTP与19次Embedding HTTP；两种模型的范围见各自报告，不能混成统一质量成功率。

Conda `astrbot`与AstrBot v4.29.3源码基线下全套`pytest -q`为1864通过，约50.53秒，只有宿主`audioop`弃用警告。新增检查覆盖历史模板字节稳定、仅替换画像段、相同schema和输入、未提交窗口在提示词/候选策略改变后暂停、分页与小预算、话题覆盖及重复查询边界。测试不证明真实模型语义通过。

独立代码复核确认默认未切换、不同正文不会因节点ID/版本相同而复用错误向量。画像探针的冻结hash覆盖脚本和模板，并未覆盖其导入的全部链执行源码；需结合本报告所在提交及保留的实际请求、候选、提交回执追溯，不能声称清单单独足以复原全部运行依赖。组合探针清单差异及零HTTP启动问题已在方法部分保留。实验材料的未定义旧爱好、结构失败和中断分支均已披露，没有改题补跑或用私人样本调优。

仍待解决：画像更新的限定与未来生效保真、无信息增量时避免改写、候选遗漏与噪声之间的取舍。新的实验应先固定未见材料、协议及恢复口径，不能将本次未通过候选直接升级为默认。上述问题目前不需要新增产品取舍，现有轻量画像、选择性抽取与来源合同继续有效。
