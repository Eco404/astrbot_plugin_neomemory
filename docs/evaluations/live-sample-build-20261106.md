## 调用时限与断点恢复

前四窗在启动后约 26.1、58.9、115.1、169.6 秒完成提交。第五窗两次调用均在约 60 秒时失败，没有获得候选；两次间隔约 5 秒，符合当前重试策略。

保留首次失败记录后，临时将抽取截止时间从 60 秒提高到 180 秒，通过维护接口对同一任务执行普通重试。此操作保留原始检查点和此前提交，仅调整网络调用等待上限。恢复后的调用约 78.4 秒返回候选，说明本次实测调用耗时超过原有 60 秒时限；该时长包括宿主可能进行的内部处理，不能据此推算单次 HTTP 耗时。

随后失败发生在候选入库校验，而非调用截止。整个任务共观察到 7 次插件级 LLM 调用尝试；未计量宿主/SDK 内部 HTTP 重试，不能把这个数量当作实际 HTTP 请求数。

结束后抽取截止恢复为 60 秒，自动抽取恢复为原值。设置 API 确认保存值与运行值一致，并与测试前完整配置相同。没有改写全局默认值。

## 精确拒绝原因

第五窗候选能通过 JSON/schema 解析，但 `node_changes[0].source_ids[3]` 引用了不存在的来源 ID：它既不属于当前 23 条来源，也不在全部 2,237 条原始记录中。

在独立副本中，对原任务重试并取得新租约，重新准备的 `input_digest` 与实机检查点完全相同。将未修改的候选交给正式 `ExtractionService.apply`，精确复现：

```text
ValueError: source_id outside the fixed extraction window
```

这是候选违反来源引用合同，不是入库校验误报。失败前后所有派生表的内容散列一致，证明整批事务回滚，没有留下部分节点、画像或来源消费记录。此前四批无重复消费、乱序或跨空间引用。

普通重试保留已经取得的候选，因此会再次校验同一个非法引用，不能自行修复它。原始候选和断点保留供维护审查；本次没有近似匹配替换 ID、删除变更项或强行激活新代。

## 语义质量

四个完成窗口的节点、版本与对应来源均已审阅；能够取得精确快照的第二至第四窗画像、关系也进行了对照。没有发现明确的说话人归属错误、否定翻转或把 Agent 建议直接写成用户既成事实。保留一项低严重度歧义：一次情境中的请求被概括为偏好，表述适用范围可能偏宽，但不足以认定它明确声称长期成立。

第五窗的**未提交候选**另有一项中等严重度问题：`coverage_changes[0]` 声明 `full`，但事件正文没有表达对应原子中的两项必要事实或条件。按现有覆盖合同不能认定完整覆盖；如果此类候选被接受，后续召回可能依据错误覆盖声明省略仍有价值的原子细节。本次候选已整体拒绝，该错误没有进入有效记忆。

成功窗口的原始模型候选没有全部留存，早期画像/关系历史也不完整，因此不能证明每个窗口从模型输出到最终状态的全部语义变化。没有完整人工答案集，不报告准确率、召回率或通用质量通过。固定用户、人格和单一会话的有限结果不能外推到其他场景。

## 后续开发依据

- 来源引用应在独立合成或公开材料上验证稳定性；检查现有开源实现的引用编码、候选约束和错误修复方式，再决定通用协议改进。本样本只保留为评估材料。
- 维护错误目前合并为 `context_or_evidence_invalid`，不足以直接定位本次错误。可增加不包含原文的细分错误码与字段位置，避免只能通过离线复现确定原因。
- 长重构复用一个任务级重试预算；多窗口中的瞬时失败会累计消耗这个预算。应在独立故障注入中评估任务级和窗口级重试边界，再调整默认策略。
- 覆盖声明的语义可信度继续按已有独立研究推进。此次观察不构成修改生产去重策略的依据，也不替代仍为 Proposed 的 ADR-0018。
- 抽取时限应结合独立输入上的实际模型延迟评估。此次临时放宽验证了恢复路径，没有据单一样本提高全局默认时限。
