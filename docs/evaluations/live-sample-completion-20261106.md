评估日期：2026-11-06，时间采用 Asia/Shanghai。实机为 AstrBot 4.29.4 测试环境，抽取使用 `ecoapi/gpt-6-luna`，向量使用 `cloudflare_bge-m3`。样本为固定用户、固定人格的一段会话，共 2,237 条原始记录：用户 1,027 条、Agent 1,210 条。

**完整构建、终态结构核验和召回路径验证已完成。** 249 个窗口消费 2,235 条来源，末尾 2 条按既有最小窗口规则保留待处理；新代已激活，84 个节点的实际向量完整且未截断。语义审阅发现 2 项画像归属问题，以及固定 20 节点样本中的 2 项明确表述问题；另有注入预算分配局限。协议、恢复和诊断问题已通用修复并部署，语义质量和预算策略仍需独立验证后继续优化。

## 范围与约束

本轮使用全部本地样本，固定重构范围，不挑选有利片段，不跳过失败窗口。此前处理 38 条后失败的旧任务已取消；短引用协议改变了输入摘要，因此以当前协议重新开始整个固定范围，随后在新任务内保留已完成窗口并恢复失败窗口。此前失败的详细证据见[首次实机评估](live-sample-build-20261106.md)。

原始记录继续使用已核验的转换结果，正文、时间、身份、来源 ID 和顺序保持不变。基础抽取提示词为 `extraction-prompt.v3`，输出 schema 为 `extraction.v2`。本轮没有依据真实对话内容调节记忆选择标准、语义提示词、窗口门限或模型候选，也未人工改写样本抽取结果。

修复涉及通用引用传输、可定位的校验错误、显式恢复流程及预算省略诊断。独立合成输入用于验证这些机制，未从真实样本改写测试题。重构期间抽取时限为 180 秒、自动抽取暂时关闭；结束后自动抽取恢复开启，保存设置与运行设置一致且无需重载生效。测试实例保留 180 秒抽取时限，这是与本轮开始前相比唯一的设置差异；插件全局默认值保持不变。

任务允许末尾不足最小抽取数量的来源继续待处理。这属于现有窗口规则；完成判断要求“已消费来源 + 合规待处理尾部 = 固定范围”，不要求强行抽取所有尾部消息，也不把进度显示 100% 当作全部消息已经消费。

原查询节点本身返回 19/20 次、直接进入注入 18/20 次；计入已单独审阅成立的完整覆盖替代后为 19/20。一次没有返回原子本身是合法事件覆盖替代；另一次查询目标已排在召回首位，但在最终装配时因预算不足被省略。这不是向量缺失或匹配失败。

这是已知内容的检索路径检查，不能据此报告自然用户问题的召回率，也不证明 AstrBot 实际聊天 hook、身份与历史路由、短期记忆或端到端互动已覆盖。本轮共 20 次向量 Provider 调用、20 段查询文本，生成式 LLM 调用为 0；没有计量 Provider/SDK 内部 HTTP 重试，不能把 Provider 调用量等同于 HTTP 请求量。

本样本只覆盖一个固定用户和人格，没有通用答案集；不报告泛化准确率。此前拒绝候选中的错误 `full` 覆盖声明仍是需要独立评估的问题，不能因为协议恢复成功就认定语义覆盖可靠。

## 重构上下文与调用规模的复核

抽取准备阶段的已有记忆选择也存在限制。`MaintenanceEngine._context_ids` 只读取缓存中的节点和消息向量；缺少向量时退回按更新时间排序的候选。本次 `extraction_context_nodes=30`。中途快照 `evidence-1793961890372739601/` 在消费1,497条来源时已有60个节点，节点向量缓存为0；检查点中的30个 `known_node_ids` 与当时最近更新的30个节点完全一致。重构管线在回放结束后才执行目标代的最终索引。

因此，“最终84个节点都有向量”不能证明前面249次抽取都取得了最相关的已有记忆。较早但相关的节点可能没有进入更新候选，影响跨窗口续写、去重和关联。这是已核实的候选准备限制；当前证据没有将某个重复节点或上述语义错误确定归因于它，也没有测得修复后的质量收益。

可优先独立验证重构过程中的增量向量准备：复用已有缓存，仅为新增/改写的节点和确有检索用途的新窗口内容补向量，以相关候选和少量近期候选共同准备抽取输入。所有候选继续绑定构建代、正文版本和固定窗口；网络调用仍在数据库事务外，最终切代前保留完整索引核验。它会增加构建期间的Embedding开销，需要同时记录调用量、复用率和候选命中效果，不能仅以“增量索引已实现”证明语义更新正确。

这一方向有现成参考：[Mem0](https://github.com/mem0ai/mem0/blob/26cdefb46600c0fa5953c4b5ee5003c125539fc4/mem0/memory/main.py#L927) 在抽取前检索已有记忆，并在新增内容时生成向量；[Graphiti](https://github.com/getzep/graphiti/blob/5c27edfa8d3e0f49b2571bcebb4261bcc89ee037/graphiti_core/graphiti.py#L1038) 将包含向量准备的节点/边写入纳入episode处理。所查本地快照与既有研究一致，均为Apache-2.0。这些路径提供实现依据，不证明其完整图结构、调用数量或质量适用于本插件；未复制代码或改变当前运行策略。

249个窗口平均约9条、大小中位数8条，其中168个窗口少于10条。120个窗口返回 `no_change` 只说明没有提交变化，不能据此判断这些调用都可省略，也不能证明没有漏掉重要内容。单空间窗口依赖前面提交的记忆与画像，单纯提高LLM并发数不会将这条重构链变成可无序执行的任务。后续性能评估应先分开计量排队、模型调用、Provider内部重试、校验、索引和人工暂停，再在独立材料上比较窗口合并或预筛选的收益与漏记代价。

- 来源归属：独立覆盖用户自述、转述他人、Agent 提案、用户采纳与未采纳等情形，验证画像选择与归因规则，避免建议升级成事实或用户优先事项。
- 事件更新：使用独立的多日、多次补充案例，检查相对时间累积、因果加强及待办状态刷新；保留允许模糊或未知事件时间的既有语义。
- 重构候选：检验相关旧节点超出近期候选范围、缓存缺失、节点改写、取消与恢复等场景；比较增量向量准备后的候选命中与新增Embedding开销，不把提高上下文条数当作已解决相关性问题。
- 证据可审计性：讨论节点版本、画像和关系更新所需的最小来源关联，避免只能用最终正文和累计引用推测修改依据。图像占位符及角色互动边界需保留不确定性。
- 注入预算：以不同语言、长度和记忆组合比较真实 token 计量、保守字节计量及结构化内容和长期命中的分配方式，明确最相关命中与画像、关系的优先级取舍；不按照本会话提高额度或改变优先级。
- 宿主集成：补充真实 hook、身份路由、历史补充查询及短期记忆的端到端验证；与当前正文自查询的服务级验证分别记录结果。
