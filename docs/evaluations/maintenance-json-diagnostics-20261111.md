# 非法候选的维护诊断验证

日期：2026-11-11（Asia/Shanghai）。范围为独立合成候选的维护引擎验证；没有读取实机失败候选、会话内容或人格，也没有调用真实模型、部署或中断实机任务。

## 当前行为

抽取候选在引用解码过程中未通过解析时，任务保存 `validation_errors`。Pydantic错误继续保存既有字段路径及类型；其他解析/顶层协议失败保存 `{"path":"$","type":"json_invalid"}`。如果异常为标准库 `json.JSONDecodeError`，另保存三个整数：

| 字段 | 含义 |
| --- | --- |
| `lineno` | 错误所在行，从1开始 |
| `colno` | 行内字符位置，从1开始 |
| `pos` | 整个候选字符串的字符偏移，从0开始 |

位置遵循Python JSON解码器的字符计数，不是UTF-8字节偏移。重复键和非有限数值由既有JSON解析回调拒绝，没有标准位置信息，因此不编造行、列或字段路径。诊断不保存异常文本、原文片段、重复键名或异常的 `doc`；原候选仍按既有契约留在任务检查点，供显式审阅与重新生成。

`json_invalid`沿用现有重新生成反馈的分类，包含JSON解析失败及顶层协议信封失败，例如顶层数组、缺失或不支持的schema版本；它不是对“所有此类输入都存在JSON语法错误”的断言。字段级schema错误仍有独立的Pydantic路径和类型。

任务仍以 `ReviewRequired / invalid_output` 失败，阻止当前空间继续自动抽取，等待人工处理。解析接受规则、提示词、重试策略、候选归档、原文和派生数据写入规则不变。维护页将任务详情交给 `pretty()`，后者使用 `JSON.stringify(value, null, 2)`，新增位置字段可以直接显示，无需修改UI。

## 合成验证

新增 [test_maintenance_json_diagnostics.py](../../tests/test_maintenance_json_diagnostics.py)，直接返回固定合成字符串，避免测试Provider的普通JSON重编码提前消除重复键。

- 四种语法/格式失败：含中文键的缺冒号、截断值、尾随文字、Markdown围栏。验证准确数值位置、保存的原候选不变及诊断不含合成敏感标记。
- 两种重复键：顶层与嵌套对象；三种非有限数字：NaN、Infinity、-Infinity。均拒绝、仅记录无内容的结构诊断，没有伪造位置。
- 两种顶层协议失败：数组和不支持的schema版本。继续拒绝，沿用现有 `json_invalid` 反馈类别。
- 一种Pydantic字段错误：保留 `node_changes / list_type`，不被改写为JSON语法错误。
- 一次显式重新生成：旧候选及诊断归档，新窗口清除旧诊断；既有 `validation_feedback` 输出的结构和内容相同，修正候选正常完成一次活动轮次。

上述解析失败均验证任务只调用一次合成Provider、不能自动领取重试、活动轮次为0且没有抽取回执；新建引擎实例读取的任务详情仍有相同诊断。恢复合法候选的测试只在显式重新生成后再次调用Provider。

未改生产代码的基线为 **12 failed / 1 passed**：12项均因缺少 `validation_errors` 失败，既有Pydantic路径验证通过。最小补丁后，新增测试与抽取诊断、重新生成、维护引擎、维护API和schema相关套件共 **133 passed，6.18秒**。新测试文件通过Ruff E/F/I/UP检查（忽略E501），补丁通过空白检查。

全量回归为 **1373 passed，35.06秒**。既有重构重新生成测试的检查点期望同步包含“新窗口清除旧诊断”，完整旧诊断继续在归档候选中核对；未改变正式重生流程已经采用的清除及归档规则。修改文件通过Ruff E/F/I/UP检查（忽略E501），全库致命错误检查和差异格式检查通过。

## 范围与限制

生产改动仅为 [core/maintenance.py](../../core/maintenance.py) 的解码异常诊断持久化，没有新异常接受分支、候选修复或额外模型调用。当前评估证明独立合成输入下的持久诊断及人工恢复行为，不证明真实模型更少生成非法JSON，也不追溯填充已有失败任务缺失的诊断。

UI兼容结论来自现有详情传递与JSON渲染代码核对；本次没有新增浏览器验证。宿主输入截断问题继续按用户决定暂不处理。
