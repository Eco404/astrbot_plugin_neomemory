# 主题判断与生产后台连续链评估

日期：2026-11-17。材料全部为独立合成内容；未读取或据私人会话调整任何提示词、规则、参数和用例。真实模型为`gpt-6-luna`与`gpt-5.6-luna`，经已配置服务及AstrBot Responses Provider调用。结构化返回不等于语义正确。

本报告的`topic_v1`是当时独立分支名称，schema为`topic-consolidation.v1`，规则尚未包含当前`topic-prompt.v2`的来源角色证据。冻结请求保存实际规则；不能将报告中的初始分支标为当前v2的完整验证。后续主体问题与验证分别见[全链](topic-full-chain-20261117.md)和[来源证据](topic-subject-evidence-20261117.md)。

## 方法与材料

固定材料与判据见`scripts/topic_cases.py`。先冻结6个案例、两分支请求、schema、模型、调用上限和无重试规则，再执行双模型比较。原始结果和全部请求保存于本地不入Git的`data/evaluations/topic-consolidation-20261117/`，manifest含固定请求与SHA256。

- `joint_v27`使用普通联合抽取，输入当前消息和已有节点，不提供已有成员图。
- `topic_v1`使用独立主题任务，输入相同经历的手写已抽取事件及已有主题成员。
- 这是任务划分和输入组织的组合比较，不是仅改变一句提示词的消融实验，也不是从原始会话抽取事件的质量评估。专用事件表述与原消息并非逐字等价，其中菜园新增活动的事件表述更明确提及另一科普合作；不能将全部差异归因于提示词。
- 6类包含持续项目、同类但无持续关联、已有主题新增成员、无变化、共享成员和纠正错误成员。所有结果均审阅，不只计算topic数量。

## 初始对照

24次HTTP调用全部返回合法协议，无重试、纠正或人工修改。

| 固定案例 | 联合v27：两模型表现 | 独立topic v1：两模型表现 |
| --- | --- | --- |
| 持续项目 | 两者均只创建新事件，没有创建主题 | 两者均创建具体主题，包含三项成员 |
| 同类但无持续关联 | 均未建主题 | 均未建主题 |
| 已有主题进展 | 均更新既有主题正文 | 均返回空changes，未加入新增成员 |
| 无实质变化 | 均无主题更新 | 均无主题更新 |
| 共享成员 | 6-luna维护一个主题，5.6-luna维护两个 | 两者均只维护科普主题，未加入菜园主题 |
| 纠正错误成员 | 均修正主题正文；原协议无法移除成员边 | 均修正正文并从最终成员集移除错误成员 |

按照预先冻结的判据，独立分支的已有主题进展和共享成员没有完全达到预期，这些失败保留。审阅同时发现材料边界存在歧义：新增活动在菜园举行，但明确属于另一科普合作；在“地点相同不证明主题归属”的规则下，模型可能把它判为场地重合。不能依据该解释把原失败事后改成通过，也不能据这两个案例认定模型普遍无法更新主题。

正文没有吞并成员事件，保留试验阶段和未承诺长期经营。主题概括仍偏事实梳理；自然第一人称允许省略“我”，此结果不证明多人格文风已经充分区分。

## 成员职责补充实验

固定原材料，另冻结一份通用职责候选，要求分别检查概况变化与成员变化、逐个判断已有主题，不把正文无变化当作成员无需更新。双模型共12次HTTP，全部结构合法，无重试或修复。

该候选仍未解决上述新增成员遗漏；6-luna在共享成员案例还改写了一个成员集合未变的主题，5.6-luna在创建案例少选了那项边界模糊活动。没有显示稳定净收益，因此没有纳入生产prompt。该后续实验是已见开发材料上的对照，不称为留出验证。

记录位于`data/evaluations/topic-membership-duties-20261117/`。请求时长中位数5.49秒，服务报告输入token合计85030、输出1581。研究分支保留于探针的`--membership-duties`选项，不能把它视为生产默认。

## 实际后台连续链

使用新的独立材料，先冻结三个步骤，再通过生产`MaintenanceEngine`、`TopicStore`、真实`SourceStore`/`MemoryStore`、AstrBot `Context`与`ProviderAdapter`执行。使用简洁主题规则，补充了只读及`summary_stale`事实说明，未采用职责补丁。第二次任务输入第一次实际提交的主题，未手填理想前态，也未替换生成正文。

脚本：`scripts/probe_topic_maintenance.py`。记录：`data/evaluations/topic-maintenance-chain-20261117/`。

| 步骤 | 两模型实际结果 |
| --- | --- |
| 两个独立项目各有两项活动 | 各创建两个范围不同的主题，各自包含正确的两项事件 |
| 新增明确属于两个项目的联合筹备会 | 同一个事件加入两个既有主题，保留主题ID及旧成员，版本均由1变2 |
| 新增无关观光经历 | 不建立泛泛主题、不加入既有项目，既有主题版本保持2 |

两条链共6个任务、6次HTTP，全部首次成功；无自然拒绝、候选纠正、任务重试或人工修复。总墙钟51.293秒。每次任务后验证事件正文及内容版本不变、活动轮次保持0、`extraction_batch_sources`保持空；说明整理没有重复消费来源或把整理当成新经历。来源、成员版本依赖和任务提交使用真实数据库。

关键授权范围、照片内部使用、会议完成与展览未举行均保留。5.6-luna一份正文用“负责”扩大了原始“参与”角色，另用“始终”概括资料使用限制，属于未消除的措辞强化风险；不能将结构和成员正确写成全部语义无误。

本链没有接向量服务，使用生产近期候选回退；事件正文为手写合成材料，没有验证会话到事件的真实抽取。没有测试长期漂移、大空间冷索引、多人群聊、实机部署及所有人格。此证据只支持在明确关系材料上创建、增量更新、多重归属和无关内容不更新的实际后台链。

## 工程与采用边界

`tests/test_topic_schema.py`的7项检查覆盖无变化、创建最小成员、更新身份与版本、去重、占位符可读长度、不接受伪造来源或成员正文操作，以及只读过期背景输入。它们是协议验证，不代替真实语义审阅。

简洁主题任务显示创建及结构维护价值，并在独立实际前态链上实现连续更新，适合接入受控使用。模糊成员归属仍须观察，不用强制成员数量或不断追加提示词把模糊案例推成通过。下一项证据应来自真实向量候选、实机整理、最终注入及回答利用；不得用本报告代替这些尚未完成的范围。
