# 事件身份与及时主题整理的独立对照

## 问题与参考

本实验检验“缺少及时主题承接是否诱发把旧事件更新成活动合集”，沿用[覆盖消费评估](coverage-consumption-20261118.md)提出的最小对照。实验不改产品提示词或合并规则，不访问实机，不使用私人会话。

先阅读[新建与更新研究](../research/event-create-update-balance.md)：Graphiti固定快照`5c27edfa8d3e0f49b2571bcebb4261bcc89ee037`（Apache-2.0）的事实边去重区分限定、日期与真正矛盾，但事实边不等于完整事件；Mem0固定快照`26cdefb46600c0fa5953c4b5ee5003c125539fc4`（Apache-2.0）保留ADD/UPDATE/NONE模板，实际默认写入却是ADD-only路径，不能拿旧模板声称已有合并机制。这里只借鉴对身份与进展分开审阅的方法，不复制代码、不复现第三方引擎，也不声称已核对当前上游。

## 冻结方法

新编3窗“街角招牌留样档案”，每窗6条合成对话，固定同一合成人格。材料包含三个日期、地点与图样都不同的采集活动，以及贯穿三窗的同一个检索目录项目。没有手写记忆节点或理想主题。

两个模型`gpt-6-luna`、`gpt-5.6-luna`各运行两条从空库独立推进的分支：

| 分支 | 任务 |
| --- | --- |
| 普通抽取 | 每窗执行生产extract，允许模型自然产生主题 |
| 按窗整理主题 | 同样extract成功后，调用现有topic_consolidate；第一窗也执行，共预定三次 |

均使用`extraction-prompt.v30`/`extraction.v7`、当前主题模板、`candidate-regeneration.v7`、json_schema与相同候选30、窗口期限120秒。已有有界自动纠正最多3次；任务级重试次数1，不人工重试、改写候选或补齐失败前态。每个模型按普通分支、整理分支的顺序执行；两个模型可以并行，模型调用总并发不超过2。

不配置向量Provider，明确使用生产近期候选回退，不测向量或召回。每次抽取记录实际准备输入与当时完整可用图，核对全部候选是否可见；候选缺失时不得将身份错误直接归为纯模型判断。主题记录真实准备闭包、成员、证据及预算裁剪。后续窗只读取各臂自己实际提交的结果。

预计12次抽取与6次主题任务；主题可能无需生成或分窗，因此首次生成上限24、实际HTTP上限32。registered与owned客户端均安装实际请求计数，SDK重试0、宿主request_max_retries=1；纠正调用、无变化主题请求、失败耗时同样计成本。无网络工具夹具只证明计数/落盘/任务衔接，不作为模型效果。

## 调用前判据

- 三次独立采集：保留时应保持各自日期、地点与图样；把首次采集事件ID扩大成全部采集的合集属于身份过度合并。选择性不存、摘要较简略与错误合并分开记录。
- 一个持续目录项目：结构搭好但未编号/未核对，随后编号完成但照片待核对、未开放，最后照片核对完成、仅志愿者内部试用、尚未公开。有旧节点可见时应沿用项目身份；重复新建、错误拆分与把目录进度归给采集事件分开记录。
- 主题职责：可承接档案及多项采集/目录的关联概况，不能吞并独立事件。普通分支若自行产生主题，报告实际差异，不能把实验称为严格的“有主题/无主题”对照。
- 逐窗审阅全部输出、前态与提交图：事件身份/粒度、合集式更新、事实主体/日期/完成与许可状态、主题成员和用途、重复文本及成本。节点数量下降不单独构成改善。
- 任一任务未成功即停止该臂；保留失败和未执行窗口，不补理想状态。两个模型各一次的小图结果不能推出普遍错误率或因果结论。

工具夹具已在禁止网络的临时库中完成4臂、18个任务；16次模拟请求钩子（两次主题任务不需要生成），全部候选可见。这只验证了工具衔接，不作为模型效果。

真实调用前已将脚本、有效配置、初始系统提示词、材料、判据与代码摘要冻结到`data/evaluations/event-topic-identity-20261118/manifest.json`。真实结果、调用、错误及人工语义审阅保留在同一忽略目录；生产代码和实机数据不改变。

### 身份与粒度

四臂都将三次采集保存为不同事件，未出现把旧采集event ID扩成后续场次合集，也没有把三张拓片的对象或完成状态互换。该目标故障未在新材料复现，不能宣称专用主题整理修复了它。

连续项目出现差异：6-luna普通分支用一个atomic承载目录进展，前两窗沿ID更新，第三窗却只把新进展写入新采集event，原目录atomic仍保留照片未核对、目录未开放的表述；第三窗输入明确包含该原子，因此不是候选没找到。其三次采集event也都重复当时目录进度。它保留了正确新进展，但跨节点的当前状态不一致，尤其旧原子未把“今天/仍未开放”限定为历史阶段。

另外三臂都沿同一目录节点更新至最后状态，保留内部试用与公开许可区别。5.6-luna普通分支有一次时间压缩瑕疵：最终目录正文把开始搭框架与完成编号并置在首次日期下，而编号实际在第二窗完成。这属于阶段时间误写，不能通过主题数量或ID连续性检查证明不存在。

按窗整理两臂后续采集event较少夹带目录进展，但都额外生成了两份与采集event近似重复的atomic。普通5.6-luna分支也有主题，且其中一次采集event仍夹带目录状态。因此主题存在并不能自动保证职责完全分开；这组有限结果不足以支持更激进合并或强制每窗建立主题。

### 主题作用与成本

6-luna按窗整理分支的topic由第一窗普通抽取自行创建并持续更新；三个专用主题任务全部返回空changes，没有改变图。该臂较好的目录连续性不能归功于专用整理，必须承认两条独立生成轨迹的随机差异。

5.6-luna按窗整理分支第一次专用任务创建了一个有依据的主题，后两窗主题正文与成员由普通抽取推进，专用任务仍返回无变化。普通分支同样由抽取自行创建并更新主题，所以这也不是严格的“有主题/无主题”因果比较。

6次专用主题调用只有1次实际新建、5次无变化；它们总计30.45秒模型等待、62,356输入token与1,018输出token。无变化请求仍有成本，且按窗整理两臂最终记忆正文与条目都更多，不能仅凭更完整概况认定净收益。本实验未测召回或回答，因此也不把额外概况称为已证实的使用收益。

## 结论

当前证据不支持把主题整理改为每窗执行，也不支持继续加重事件合并规则。保持现有低频主题机制；事件/主题边界先观察完整构建中的实际身份变化，不能用条目数代替语义判定。新的通用问题是持续状态节点可见却漏更新，以及阶段时间被压缩；需独立设计更长链、多次运行才能判断稳定程度，本次不据此改生产提示词。

若后续继续对照，必须明确控制“主题本身产生的内容变化”与“执行一次空变化主题任务”区别；不能把普通抽取自行生成topic后的全部好转算作专用整理收益。应同时保留旧节点可见性、实际ID演进、逐次状态和调用成本证据。

完整逐窗审阅见忽略目录`semantic-review.json`，成本汇总见`aggregate.json`，运行结束再次核对冻结摘要未变，见`completion-checks.json`。没有私人材料调优、生产规则修改或实机写入。
