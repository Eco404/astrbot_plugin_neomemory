## 1. 开发基线

当前用于宿主适配和集成测试的 AstrBot 工作副本是 `v4.29.3`，提交为 `abf683071`。第一阶段默认固定在该版本上开发，不在没有兼容性测试的情况下跟随 `master`。需要验证其他版本时，使用独立工作副本或显式 tag，并在测试报告中记录版本。

Python 命令优先通过 Conda 环境 `astrbot` 执行。当前环境已能运行 `conda run -n astrbot python`。插件测试分为两层：不启动宿主的纯 Python 测试，以及将插件装入 `/workspace/astrbot/AstrBot` 后执行的宿主集成测试。

AstrBot 相关代码只依赖公开插件接口：

- 事件使用 `AstrMessageEvent` 的 `unified_msg_origin`、`get_platform_id()`、`get_platform_name()`、`get_message_type()`、`get_group_id()`、`get_sender_id()`、`get_sender_name()`、`get_message_str()` 等方法。
- 插件入口继承 `Star`，数据目录使用 `StarTools.get_data_dir()` 获取，不硬编码宿主目录。
- 页面 API 使用 `Context.register_web_api()` 和 `astrbot.api.web`，视图使用 `views/<view_name>/index.html` 与 `window.AstrBotPluginView`。
- 模型调用通过 `Context` 的 Provider 方法；不从插件内部直接依赖宿主私有 Provider Manager 实现。
- `astrbot_plugin_livingmemory_origin` 只用于核对事件过滤、后台任务和错误处理方式，不作为 NeoMemory 的数据库或配置兼容目标。

如果宿主接口在开发中发生变化，先在适配层记录差异和测试用例；不要把兼容分支散落到存储、身份和记忆逻辑中。

## 4. 阶段 0：开发基线与插件骨架

### 4.1 目标

建立可以持续开发的最小插件，而不实现记忆抽取或召回。完成后，插件能够被 AstrBot 识别、初始化、关闭，并提供一个不读写业务数据的健康检查接口。

### 4.2 内容

- 建立 `main.py`、`metadata.yaml`、`_conf_schema.json`、`requirements.txt` 和包目录。
- 建立统一的插件数据目录解析，规划 `source.db`、`memory.db`、`cache.db` 路径，但不提前创建无用表。
- 建立配置读取、默认值、版本号和错误日志规范。
- 建立 `tests/`，包含无宿主的 fake event、fake context、临时数据目录和测试数据库夹具。
- 编写 AstrBot v4.29.3 宿主探针：加载插件、执行最小事件、调用健康 API、关闭插件并检查后台任务是否结束。
- 确定 SQLite 访问实现。先以一个小型 benchmark 比较 `aiosqlite` 和 `sqlite3 + 专用线程执行器`；选择结果写入开发记录，不让存储实现泄漏到业务模块。
- 建立数据库迁移编号规范和测试数据库隔离规范。

### 4.3 非目标

- 不注册 LLM recall hook。
- 不调用 LLM 或 Embedding。
- 不写入聊天内容，不实现长期记忆节点和完整 WebUI。

### 4.4 退出条件

- 在 `conda run -n astrbot` 环境中，AstrBot v4.29.3 能加载和卸载插件。
- 健康 API 返回插件版本、数据库路径状态和后台任务数量，但不暴露密钥和原文。
- 单元测试、迁移空库测试和宿主加载探针通过。
- 插件异常初始化时不会阻塞 AstrBot 主循环，且能给出可定位日志。

## 5. 阶段 1 身份与原始事实库（历史详细计划）

### 5.1 目标和边界

本阶段的唯一目标是把输入可靠地保存为可重放的原始事实，并为后续派生记忆提供稳定身份和顺序。阶段结束时可以回答“这条输入来自谁、哪个平台/群、哪个人格、何时观察到、是否已经写入”，但还不能回答“这条输入应该形成什么记忆”。

本阶段明确不做：LLM 抽取、Embedding、向量检索、衰减、主题归并、画像生成、人格关系推断、完整人工治理、导入导出、原始库自动清理和完整五栏 WebUI。

### 5.3 原始库 v1 数据模型

第一阶段只建立 `source.db`，采用显式迁移而不是启动时散落 `CREATE TABLE IF NOT EXISTS`。建议表和职责如下：

#### `conversation_streams`

表示一条输入流，用于顺序、去重和后续抽取游标。

- `stream_id TEXT PRIMARY KEY`：由来源类型、平台实例、会话和必要的作用域信息稳定生成。
- `platform_instance_id TEXT NOT NULL`：对应 `event.get_platform_id()`。
- `platform_name TEXT NOT NULL`：对应 `event.get_platform_name()`，仅作展示和诊断。
- `message_type TEXT NOT NULL`：私聊、群聊或其他类型。
- `conversation_id TEXT NOT NULL`：保存 `event.unified_msg_origin`，只表示输入流，不作为长期记忆归属。
- `group_id TEXT`、`persona_id TEXT`：可为空，但若事件有值必须保存。
- `next_sequence INTEGER NOT NULL DEFAULT 1`、`last_observed_at REAL`。

#### `source_records`

保存每条原始输入，是重构的主要事实来源。

- `source_id TEXT PRIMARY KEY`：优先使用宿主消息 ID；没有稳定消息 ID 时由输入流、角色、顺序和内容哈希生成。
- `stream_id TEXT NOT NULL REFERENCES conversation_streams(stream_id)`。
- `source_type TEXT NOT NULL`：第一阶段支持 `conversation`，保留 `source_event` 枚举。
- `actor_kind TEXT NOT NULL`：`user`、`agent`、`system`、`external`。
- `actor_account_id TEXT`、`actor_logical_user_id TEXT`：保留账户和当时的逻辑用户解析结果。
- `content_text TEXT NOT NULL`：规范化文本或组件占位符。
- `content_json TEXT`：必要时保存可审查的消息组件 JSON，不作为业务查询的唯一文本来源。
- `observed_at REAL NOT NULL`：插件观察到消息的时间。
- `event_time_start REAL`、`event_time_end REAL`、`event_time_text TEXT`：第一阶段只保存可获得值，不由程序猜测事件时间。
- `sequence_no INTEGER NOT NULL`：在 `stream_id` 内单调递增。
- `message_id TEXT`、`source_hash TEXT NOT NULL`、`metadata_json TEXT`。
- `created_at REAL NOT NULL`、`schema_version INTEGER NOT NULL`。

对 `(stream_id, message_id)` 建唯一约束；没有 `message_id` 时使用生成的 `source_id` 去重。相同消息重复到达必须返回已有记录，不增加 sequence，也不触发后续任务。

#### `logical_users`

- `logical_user_id TEXT PRIMARY KEY`。
- `display_name TEXT`、`created_at REAL`、`updated_at REAL`、`status TEXT`。

首次看到一个未绑定账户时，创建一个只对应该账户的逻辑用户；这不是跨账户推断。账户合并只能通过后续显式绑定操作完成。

#### `account_bindings`

- `platform_instance_id TEXT NOT NULL`。
- `account_id TEXT NOT NULL`。
- `logical_user_id TEXT NOT NULL REFERENCES logical_users(logical_user_id)`。
- `binding_status TEXT NOT NULL`：`active`、`disabled`、`conflict`。
- `created_at REAL`、`updated_at REAL`、`source TEXT`。
- 主键为 `(platform_instance_id, account_id)`，同一账户不能同时指向两个活动逻辑用户。

#### `source_participants`

保存群消息中的发送者、被提及者和 Agent 等参与者，避免把参与者文本复制到每条业务记录中。

- `source_id TEXT NOT NULL`。
- `participant_kind TEXT NOT NULL`。
- `account_id TEXT`、`logical_user_id TEXT`、`display_name TEXT`。
- 主键为 `(source_id, participant_kind, account_id, logical_user_id)`。

#### `source_cursors`

保存后续抽取所需的游标，但第一阶段只维护写入范围和最后确认的 sequence，不消费游标。

- `stream_id TEXT PRIMARY KEY`。
- `last_captured_sequence INTEGER NOT NULL`。
- `last_derived_sequence INTEGER NOT NULL DEFAULT 0`。
- `updated_at REAL`、`cursor_version INTEGER`。

第一阶段至少建立索引：`source_records(stream_id, sequence_no)`、`source_records(observed_at)`、`source_records(actor_logical_user_id)`、`source_participants(logical_user_id)`。

### 5.4 身份解析顺序

身份解析必须是纯函数或可测试的适配器，不把解析逻辑写进事件 listener：

1. 读取平台实例、平台名称、消息类型、`unified_msg_origin`、群组 ID、发送者账户 ID 和消息 ID。
2. 将平台账户映射到 `account_bindings`；不存在时创建一个默认逻辑用户和绑定。
3. 通过 `PersonaResolver` 获取当前实际人格 ID。第一阶段只保存宿主解析得到的 ID；若宿主在该事件时机不能可靠提供人格，保存 `persona_id=NULL` 并标记 `identity_pending`，不能把猜测的名称当作事实。
4. 生成 `stream_id` 和 `memory_space_id` 候选。私聊长期空间使用 `persona_id × logical_user_id`，群聊输入流保留 `persona_id × platform_instance_id × group_id` 所需字段。
5. 将解析结果写入原始记录的快照字段，同时保留原始账户和平台字段，后续绑定变化不会篡改历史事实。

阶段一不实现跨账户自动匹配；账户合并只准备数据结构和维护 API 的占位，不提供模型猜测。

### 5.5 事件接入方案

事件接入分为用户/外部输入和 Agent 输出两条路径：

- 用户和群消息使用公开事件过滤器接收。群聊旁听沿用 LivingMemory 的“自定义过滤器中调度后台保存、返回 `False` 不唤醒主链”思路；必须先验证当前 AstrBot 版本的过滤顺序。
- Agent 输出使用 `on_llm_response` 或等价的宿主回调保存为 `actor_kind=agent`，并用事件上下文和响应标识去重。平台回显不能再次写成新的 Agent 记录。
- 私聊消息不应只依赖 `on_llm_request`，因为命令、被过滤消息或没有进入主链的消息可能遗漏。阶段 0 的宿主探针必须确定一个不会额外唤醒 LLM 的全量输入入口；如果当前版本没有稳定入口，记录限制并先覆盖进入插件处理阶段的消息。
- 所有事件处理器只负责规范化和提交原始记录，不调用 LLM、Embedding 或记忆节点服务。

规范化对象至少包含：`source_id`、角色、文本、消息组件摘要、平台实例、平台名称、消息类型、会话来源、群组、账户、逻辑用户、人格、观察时间、可选事件时间、顺序和原始元数据。

### 5.6 写入和并发规则

- 原始记录提交以单条或小批次事务完成，事务内只包含身份快照、sequence 分配、source record、participants 和 cursor。
- 网络调用不得发生在数据库事务内。
- 同一 `stream_id` 的 sequence 分配和重复判断必须串行；不同 stream 可以受限并发。
- 数据库写入失败时保留内存中的规范化对象和错误日志，允许维护任务重新提交；不能丢弃事件后继续推进 cursor。
- 进程关闭时等待有限时间完成写入任务；超时任务不标记为成功，重启后由 message ID/`source_id` 幂等补写。
- `source.db` 使用 WAL、外键和明确的 busy timeout；具体 SQLite 执行器在阶段 0 的 benchmark 后确定。

### 5.7 最小配置

阶段一只暴露影响输入收集和安全边界的配置：

- `enabled`：是否启用原始记录。
- `capture_private_messages`：默认开启。
- `capture_group_messages`：默认开启，但只记录到达插件阶段的消息。
- `capture_agent_messages`：默认开启。
- `data_dir`：只读展示或由宿主数据目录推导，不允许页面随意写绝对路径。
- `max_content_chars`：异常超长消息的截断上限；原始组件摘要保留截断标记。
- `write_batch_size` 和 `write_flush_timeout_ms`：只控制写入，不触发抽取。

阶段一不加入 LLM Provider、Embedding Provider、抽取阈值、召回权重和衰减参数，避免配置页提前出现没有实现的选项。

### 5.8 最小查看页面

阶段一只提供一个最小插件 View，用于验证宿主页面和数据通路：

- 显示插件版本、宿主版本、数据库迁移版本和最近一次写入状态。
- 显示可选择的记忆空间候选，但只展示来源流和身份快照，不展示“长期记忆”节点。
- 提供最近原始记录分页查看和按 stream/角色过滤。
- 不提供编辑、删除、重构、导入导出和模型测试按钮。

页面 API 必须经过服务层，不能直接在 handler 中拼 SQL。查询失败只返回错误状态和 request ID，不返回异常堆栈。

### 5.9 阶段一测试矩阵

#### 纯函数和单元测试

- 平台、消息类型、会话、群组、账户和人格字段规范化。
- 默认逻辑用户创建、显式账户绑定和绑定冲突。
- 私聊、群聊、Agent、system 和 `identity_pending` 的作用域字段。
- source ID、message ID、内容哈希去重。
- stream sequence 的连续性和并发提交。
- 超长文本、空文本、组件消息、缺少 sender/message ID 和异常时间。
- schema 迁移从空库初始化、重复执行和版本不支持。

#### 宿主集成测试

- 在 AstrBot v4.29.3 中加载、卸载和重载插件。
- 构造私聊和群聊 `AstrMessageEvent`，验证公共事件方法读取结果。
- 验证群旁听过滤不会唤醒主链，不会产生 LLM 请求。
- 验证 Agent 响应保存一次，平台回显和重复 hook 不产生第二条。
- 关闭并重启插件后，source.db 中的 sequence 和去重状态保持。
- Web API 能查看迁移状态和最近记录，浏览器关闭不影响写入任务。

#### 故障测试

- 数据库忙、磁盘不可写、迁移失败、写入取消和进程在提交前退出。
- Provider 不可用时阶段一仍能保存原始输入，因为阶段一不依赖 Provider。
- 身份解析失败时保存原始账户和 `identity_pending`，不得写入错误的长期空间。

### 5.10 实施顺序

按以下小步推进，每一步都先添加测试：

1. 建立插件骨架、元数据、配置和健康 API。
2. 建立 SQLite 执行器、迁移表和测试数据库夹具。
3. 实现 `source.db` v1 schema、source store 和幂等写入。
4. 实现身份规范化、默认逻辑用户和显式账户绑定。
5. 接入私聊/群聊原始输入，完成自定义过滤器的宿主探针。
6. 接入 Agent 输出保存和重复回显防护。
7. 增加最小 View、分页查询和迁移/写入状态接口。
8. 执行宿主集成、重启恢复和故障测试，补充 `docs/schema/source-v1.md`。

### 5.11 阶段一退出条件

只有同时满足以下条件，阶段一才算完成：

- 私聊、群聊和 Agent 原始记录可以写入 `source.db`，并能在重启后继续。
- 每条记录都有稳定 `source_id`、来源流、角色、观察时间、顺序和身份快照。
- 重复事件不会重复写入，也不会推进 sequence 或 cursor。
- 同一输入流串行、不同输入流可受限并发；写入失败不会静默丢数据。

## 18. 覆盖与输入完整性研究及后续入口

[计划](../../覆盖与输入完整性轮次实施计划.md)与[执行复核](../../覆盖与输入完整性轮次执行记录.md)分别落实路线1B/1C。覆盖通过实际生产选择器完成99个离线单元：默认2048字节/6节点下停止覆盖省略保留22/22项人工标注事实，原策略17/22，累计文本多28.4%；受限预算会挤掉其他信息，不能当作普适收益或实测token成本。逐字包含在历史/未核实引用中仍然误省略，不作为语义证明。覆盖默认未改，具体取舍见ADR-0018。
