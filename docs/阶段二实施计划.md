# NeoMemory 阶段二实施计划：派生节点与基础记忆库

> 状态：已完成实现，阶段复核中  
> 对应目标：建立可被抽取、召回和人工治理复用的 `memory.db` 稳定服务接口

## 1. 阶段目标

阶段二只建立派生记忆的确定性基础设施。完成后，程序可以在明确的记忆空间和 generation 中创建、查询、修改和停用记忆节点，并能追溯到 `source.db` 中的原始来源。后续抽取阶段可以把模型输出转换为这些服务接口的输入，维护阶段可以复用同一套版本和状态语义。

本阶段不调用 LLM 或 Embedding，不实现自动抽取、被动召回、衰减、任务队列、完整 WebUI、拆分/合并交互、导入导出和原始库清理。

## 3. v1 数据边界

`source.db` 是原始事实库，`memory.db` 是可删除、可重建的派生库。两个库不在 SQLite 层建立跨数据库外键；`node_sources.source_id` 由服务层验证格式，并允许注入 `source_exists` 校验器连接阶段一的 `SourceStore`。没有校验器时仍允许人工创建带外部来源说明的节点，但接口会拒绝空来源 ID。

### 3.1 记忆空间与 generation

- 私聊空间唯一键：`persona:<persona_id>:user:<logical_user_id>`。
- 群聊空间唯一键：`persona:<persona_id>:platform:<platform_instance_id>:group:<group_id>`。
- `memory_spaces` 保存结构化作用域字段和唯一 `scope_key`。
- 每个空间创建一个初始 active generation；后续 generation 默认 `building`，由显式切换接口原子激活。
- 同一空间最多一个 active generation。切换时旧 generation 变为 `retired`，失败 generation 不影响当前 active generation。

### 3.2 节点与版本

- 节点类型只有 `atomic`、`event`、`topic`。
- 节点正文放在 `memory_node_versions`，节点保存当前版本号和稳定元数据。
- 正文实际变化必须新建版本、递增 `content_version`、重新设置强度；只增加来源、关系、参与者或覆盖信息不创建正文版本。
- 状态支持 `active`、`historical`、`disabled`、`superseded`、`deleted`、`manual_protected`。
- `manual_protected` 作为状态表达人工保护；恢复为 `active` 即解除保护。第一版不实现保护候选队列。

### 3.3 关系与来源

- 关系类型限制为 `contains`、`related`、`follows`、`supersedes`。
- 边的两个端点必须属于相同空间和 generation，禁止跨空间污染。
- `node_sources` 只保存引用，不复制原文；删除节点不删除 `source.db` 原始记录。
- `node_coverage` 表示事件正文覆盖的原子节点及其内容版本，用于未来召回时避免重复展开。

### 3.4 画像、人格关系、短期状态和笔记

- `user_profiles` 按 generation、空间和逻辑用户唯一；标签使用 JSON 数组，描述为短自然语言。
- `relationship_states` 按 generation、空间和逻辑用户唯一，保存人格对用户的主观状态，不改变原始事实归属。
- `short_term_states` 按 generation、空间和 conversation 唯一，保存滚动摘要和覆盖范围；重构时可随 generation 重建。
- `notes` 默认绑定当前空间和人格，不绑定 generation，使自主笔记不因派生记忆重构而丢失。

## 4. 服务接口

`MemoryStore` 的公共接口必须是异步的，网络模型调用不进入数据库事务。第一版至少提供：

1. `open/close/health`。
2. `get_or_create_space`、`get_space`、`get_active_generation`。
3. `create_generation`、`activate_generation`。
4. `create_node`、`get_node`、`list_nodes`、`update_node_content`、`update_node_status`。
5. `add_node_source`、`remove_node_source`、`list_node_sources`。
6. `add_edge`、`remove_edge`、`list_edges`、`add_coverage`。
7. `upsert_profile`、`list_profiles`。
8. `upsert_relationship`、`get_relationship`。
9. `upsert_short_term`、`get_short_term`。
10. `create_note`、`update_note`、`list_notes`。

所有写入接口都在一个明确事务内完成；重复的空间、generation、版本、来源和关系写入应返回已有记录或稳定错误，不产生隐式重复。

## 5. 实施顺序

1. 写入本阶段 schema 文档和迁移版本规范。
2. 增加空间、节点、状态、画像和笔记的纯校验模块。
3. 实现 `memory.db` v1 迁移，启用 WAL、外键和索引。
4. 实现空间和 generation 服务，再实现节点及版本服务。
5. 实现来源、参与者、关系和 coverage 服务。
6. 实现画像、人格关系、短期状态和笔记的最小 upsert/query。
7. 用阶段一的 source fixture 验证来源追溯和不存在来源拒绝。
8. 运行全量测试、迁移重复执行测试和 AstrBot 插件加载回归。

## 6. 测试矩阵

- 空库迁移、重复迁移、外键和唯一索引。
- 私聊/群聊 scope key 的确定性和空间隔离。
- generation 创建、唯一 active 和失败切换保留旧 active。
- 节点创建、当前版本查询、正文版本递增和强度重置。
- 仅新增来源/关系不递增正文版本。
- 状态转换、软删除、人工保护和默认 active 查询。
- 来源引用去重、来源存在性校验和节点删除不影响 source.db。
- 关系端点跨空间拒绝、coverage 类型校验。
- 画像、人格关系、短期状态和笔记 upsert 幂等性。
- 并行不同空间写入不互相污染；同一数据库事务失败回滚。

## 7. 退出条件与回滚

阶段二完成必须满足：

- 新建的 `memory.db` 可从空库迁移到 v1，重复启动不产生重复 schema。
- 手工构造节点可以查询、修改、禁用、恢复和删除；正文版本与状态语义符合 ADR-0003/0008。
- 节点、关系和画像严格隔离在空间及 generation 内，来源引用可查询且不复制原文。
- 重启后数据保持，事务失败不留下半个节点或半条关系。
- 阶段一的 13 个测试和阶段二新增测试全部通过，Ruff 与 `py_compile` 通过。

回滚时停止调用 `MemoryStore` 新入口即可；`memory.db` 是独立派生库，可删除后从 `source.db` 重建。不得为回滚修改或删除 `source.db`。

## 8. 明确遗留项

自动抽取、LLM schema、向量缓存、衰减、后台任务和人工拆分/合并属于后续阶段。阶段二只保证这些功能未来有稳定的数据边界，不提前实现空壳模块。
