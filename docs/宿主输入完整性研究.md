# 宿主输入完整性研究与隔离复现

日期：2026-11-02（UTC+8）。范围：路线 1C，AstrBot v4.29.3 / `abf683071`，非流式纯文本抽取。**本轮确认了输入缺失仍可能提交成功的工程路径，没有修复生产 Provider，也没有证明真实模型或用户数据已经发生该问题。**

## 结论与现有接口边界

NeoMemory 的 v3 抽取输入只有两条消息：system 是规则/schema，user 是包含人格、全部 sources、已有节点/画像/关系的 JSON。宿主 OpenAI Chat Provider 捕获上下文超限错误后，调用 `pop_record()` 删除最多两条非 system 消息再请求。对于这一形态，第二次请求仅剩规则，全部待抽取数据都被删除。

模拟服务端第二次返回结构正确的 `no_change` 时，真实 `ExtractionService.run()` 能通过校验、写入凭据、推进一轮活动并消费来源。凭据中的 `input_digest` 证明插件准备过何种输入，不能证明实际传输过何种输入。宿主先深拷贝 contexts，因此调用后检查原消息未改变也无法发现问题。

`request_max_retries=1` 只约束 `retry_provider_request()` 的网络错误层；它不关闭外层内容回退。永久的上下文错误可产生 10 次模拟发送，其中第 2～10 次只有 system。插件总超时仍有效，不能把网络重试参数解释成整体 HTTP 次数硬上限。

核对当前 `Context.llm_generate()`、抽象 `Provider.text_chat()` 及 OpenAI Chat/Responses 实现后，未找到公开的“禁止修改输入”参数、逐发送校验回调或可信输入回执。任意额外 kwargs 可以被接受而忽略，因此不能通过盲传一个新名称来声明受到保护。

## 隔离复现与准确证据

[test_host_input_integrity.py](../tests/test_host_input_integrity.py) 复用前轮真实宿主测试装配；HTTPX `MockTransport` 是唯一传输。创建的 source.db / memory.db 均在 pytest 临时目录，所有输入、人格、key和模型名都是独立合成。测试不调用线上服务。

| 场景 | 模拟发送及请求内容 | 事务结果 |
|---|---|---|
| 第一次上下文超限，第二次合法 `no_change`；分别采用默认网络重试及 `request_max_retries=1` | 每种均 2 次；先完整 system+user，后仅 system；调用前后原 messages 与 Provider 配置均未改变 | 均写入抽取凭据；活动轮次 0→1；来源记为已消费；节点为空。这是已知缺陷复现，测试通过不代表修复成功。 |
| 第一次 HTTP 503，第二次合法 `no_change` | 2 次；两次完整消息一致 | 正常提交；说明网络重试本身不必删输入。 |
| 永久上下文超限，网络尝试参数为 1 | 10 次；第 1 次完整，其余仅 system | 最终异常；无抽取凭据、无来源消费。 |
| 上下文回退后为空响应、非法 JSON、一般 HTTP 400 | 每种 2 次 | 分别失败；无凭据、无来源消费、活动轮次仍为 0。 |

| 同一 Provider 并发两次调用，其中一次上下文回退 | 总共 3 次；A完整、B完整、A仅system | B输入和两份调用方原对象没有被A回退修改，Provider配置不变。只证明该合成单key场景，不能证明所有Provider并发语义。 |

## 为什么本轮不在插件中强行拦截

- 不临时更改共享 Provider 配置、`_handle_api_error`、SDK客户端或全局重试方法。这些方式会影响普通聊天与并发任务，还绑定宿主私有实现。
- 不把 source JSON 移到 system 来躲避 `pop_record`。这改变信任边界，且不能阻止后续其他输入变更。
- 不把调用后消息对象比对、非空响应、合法 schema、来源 ID 校验或 `input_digest` 当作实际发送完整性证明。
- 不在生产安装实验用的 HTTPX hook。实验专有客户端可控制发送；生产共享 Provider 的传输没有对应公开扩展契约。
- 不把所有 Provider 固定为单次网络尝试来冒充修复。它会失去有用的瞬时故障恢复，同时仍保留内容回退。

本轮因此不修改 [providers.py](../adapters/providers.py)；正常读取、召回、治理和原始记录保留不因本项研究改变。宿主能力缺口保留为明确待解决问题。

## 纯插件备选：窗口校验值回显（协议探针）

在user JSON中加入 `window_receipt`，system只说明必须原样回显该字段，**不包含它的值、默认值、schema const或示例值**。无论 `changes` 还是 `no_change`，候选都必须包含正确值；由插件在事务应用之前检查，缺失/不一致立即失败且保留来源。对于当前host删除整个唯一user的路径，第二次模型请求拿不到该值，错误no_change会被拒绝。它不能阻止第二次发送，也不能提供统一HTTP预算。

可以比较两种生成方式：

- 随机nonce：足够长且不可预测，每份准备好的窗口生成一次并持久保存为恢复必要数据，候选重试复用同一nonce；重新准备才换值。它会增加状态字段与迁移，不能存入可清空缓存。
- 窗口摘要：以域分隔字符串和现有 `PreparedExtraction.input_digest` 计算SHA-256，值只放user中，重试可确定性恢复，不必新增随机状态。它建立与该快照的绑定；模型只需抄值，不让模型自行计算hash。**抄对摘要不等于它收到或使用了摘要所代表的全部内容。**

独立测试使用第二种方式以及模拟服务端“只回显当前请求中可见的值”，没有修改生产schema或提示词。结果：

| 协议探针 | 结果 | 证明范围 |
|---|---|---|
| 完整输入，模拟响应正确回显 | 通过且可提交 | 校验路径机械上可行；不代表真实LLM遵循率已测 |
| 当前宿主整条user回退消失 | 2次模拟发送后因缺少receipt拒绝，无来源消费 | 可以缓解这一特定完整消息丢失路径 |
| 模拟另一个Provider只清空sources、保留receipt | 仍能通过并消费 | 明确反例：不能作为任意局部截断或语义完整性的证明 |

nonce不可预测可降低错误猜中概率，但回显仍是模型输出，不是可信传输回执；服务端复用状态、字段泄漏进system、伪造响应等都不在这个探针的保证范围。真实模型还可能漏字段或抄错，从而增加本来可成功窗口的暂停率。正式采用需要新schema/提示词版本、连续更新及旧候选恢复策略、独立真实API遵循率测试，不能直接在生产v2解析器中偷偷放宽字段。

额外查找了上述参考项目的 `nonce`、`receipt`、`input hash/digest`、`request_id` 等实现。在所读记忆LLM客户端中未找到与这一整消息删除缓解直接等价的成熟协议。Hermes的 [JSON-RPC请求ID](https://github.com/NousResearch/hermes-agent/blob/d0509566/agent/copilot_acp_client.py) 会核对响应ID，`api_request_id`也用于调用关联；它们是可信传输关联，不能据此宣称模型回显已经获得同等保证。这一备选因此标为独立协议实验。

## 最小宿主方案与独立候选补丁

建议先对宿主提供**逐调用、纯文本输入完整性**契约，不需要重建客户端。可采用以下公开接口设计，名称和兼容策略需要在后续宿主改动前定稿：

1. `Provider.text_chat(..., *, allow_context_truncation: bool = True, ...)` 显式声明参数；`Context.llm_generate()` 逐调用转发。`True` 保留现有调用的行为；插件请求 `False` 时，遇到上下文超限直接抛出有类型的异常，必须在 `pop_record()` 和下一次发送之前退出。
2. OpenAI Chat 和 Responses 都必须实现并转发；Responses 不能在继承处理后重新组装已经删减的 input。非流式为本轮目标；流式只有实现和验证同一契约后才能声明相同能力。
3. 这个布尔参数本身只解决上下文截断。若宣称更广的 `immutable_text_input.v1` 能力，还必须核对所有发送前变更入口：普通文本消息顺序、角色和正文不被删改；`custom_extra_body` 不允许覆盖 messages/input/system；模型专用转换不得删正文；图像、工具等不在该能力范围的输入在请求前明确拒绝，不能静默降级。必要的协议字段重编码可以允许，但必须保留输入含义，测试应比较解码后的正文与顺序。
4. 对纯文本非流式的网络错误，继续允许既有有界重试，但每次使用相同输入；与完整性不同的“实际发送次数上限”应另设明确语义。429 key轮换、SDK和宿主重试均纳入预算设计，不能只凭 `request_max_retries` 计数。
5. 能力发现使用公共的、可版本化的 Provider capability（例如 `immutable_text_input.v1`）；基类默认不声明，只有经完整实现与契约测试的具体 Provider 才声明。参数名称出现在 `**kwargs`、宿主版本号或一次成功连通测试都不足以确认能力。没有统一capability API时，过渡方案只能是明确列出的已验证Provider类与宿主版本，并显式检查方法签名；不要对未知类乐观放行。
6. 插件的严格抽取路径在调用前验证能力，不支持时返回可维护的“不支持输入完整性保护”任务错误，保留来源与检查点，不发请求、不提交 no_change、不影响采集和查询。模型页展示支持范围。此严格门槛何时成为默认，以及旧宿主是否允许用户显式选择带已知缺口的兼容模式，需要产品决定，不能本轮静默让当前全部模型失效。

宿主候选必须通过以下契约用例后再接入插件：关闭开关时上下文错误仅发送一次且来源不消费；默认开关兼容旧行为；重复网络请求正文一致；并发不同调用的开关独立；取消/截止不追加发送；Responses共享回退路径受保护；不支持能力与保留字段覆盖在发送前拒绝；空/异常响应不提交。若仅验证其中一部分，应缩小能力名称与宣称范围。

针对上述方案中范围最窄的“上下文超限时不删除消息”，已生成[候选patch](patches/astrbot-v4.29.3-no-context-truncation.patch)与[使用/许可说明](patches/README.md)，仅应用在 `data/references/astrbot-input-integrity/` 的独立worktree。现用 `/workspace/astrbot/AstrBot` 未改，插件也没有接入新参数。

补丁明确声明能力 `no_context_truncation.v1`，**没有声明 `immutable_text_input.v1`**：基类默认不支持；仅精确的 `ProviderOpenAIOfficial` 与 `ProviderOpenAIResponses` 两个已验证具体类各自声明，未知子类即使继承生成入口也不会自动继承声明。`allow_context_truncation=True`保持默认行为，`False`在既有上下文错误分类命中后直接重新抛出原异常，发生在删除消息及再次请求之前；非布尔参数在首次发送前拒绝。Context现有kwargs转发即可，不改共享配置。补丁覆盖非流式及流式入口；流式仅验证首次请求即上下文错误的路径，没有验证中途已经产出内容之后的回退。

[独立契约测试](../tests/host_input_patch_contract.py)仅通过显式路径运行，默认全量测试不会在未打补丁的宿主上收集它。Chat与Responses均验证：严格模式只发送一次、保留来源；默认模式仍回退；网络重试保留完整输入；空输出失败；并发两种开关互不影响；取消不追加发送；无效参数不发送；基类、覆盖入口或仅覆盖 `_query` 的未知子类不自动声明能力。最终候选独立契约 **22 passed**；现用宿主边界/适配测试为前述 **47 passed**。补丁应用检查通过。它是可审阅且经模拟验证的局部候选，不是已部署修复；更广的输入变更、实际HTTP预算和其他Provider仍待实现。Responses继承同一个公开生成入口，独立修改仅用于明确声明这个具体类的能力。

| 后续选择 | 收益 | 成本与仍有的边界 |
|---|---|---|
| 宿主公开能力/候选补丁 | 在已知内容回退发生前停止，无需LLM回显；不增加抽取协议负担 | 需要明确宿主版本或补丁维护策略；未知Provider如何处理需决定；当前patch只阻止上下文超限删消息 |
| 纯插件receipt缓解 | 无须修改宿主，可拦截唯一user被删后缺失/错误校验值的候选 | 需要新schema/提示词及真实LLM遵循率验证；不能避免第二次发送，不能证明任意局部输入完整 |

建议优先选择宿主能力路线，并将“不支持时保留待处理窗口”的行为明确展示。若产品要求先维持纯插件兼容，可先验证receipt作为标明边界的过渡防线，不把它命名为完整输入保证。两者可以组合，但本轮不同时增加生产协议与宿主依赖。当前受支持宿主版本、未知Provider兼容策略及是否维护补丁需要一起决定。
