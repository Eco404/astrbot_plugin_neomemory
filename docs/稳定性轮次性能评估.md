# 稳定性轮次：有界召回 profiling 与局部优化

日期：2026-10-29（UTC+8）。本轮接续[阶段六规模评估](阶段六规模评估.md)，使用 [benchmark_console.py](../scripts/benchmark_console.py) 和真实的存储、Embedding、召回服务。数据及向量全部为离线合成；没有读取聊天原文、密钥，没有网络调用，也不具备语义评测能力。

## 目标与方法

阶段六的热召回 P95 约 865 ms，只说明整体开销。本轮先量化候选快照、缓存读取、JSON 解码校验、缓存向量归一化、排名、正文选择和注入前复核，再修改确定的热点。

所有观测包装器仅在脚本中启用，不进入生产服务或数据库。同步 worker 时间包含该 worker 执行期间的墙钟时间；调用方时间包含线程排队与调度等待。`cache_total_including_decode` 包含 `cache_decode_validation_worker` 和 `cache_sql_touch`，不能相加重复计算。触碰 LRU 的 SQL 测量包含 `executemany`，不包含其事务提交；未单独分解的剩余开销不能直接归因于 SQLite 查询或磁盘。

参数与阶段六相同：大空间 2,100 节点，另有 24 个小空间各 20 个节点；维度 768；当前查询 + 最近 10 条 user/agent 消息；batch size 16；Embedding 并发配置 2；被动截止 1.5 秒。共享候选上限仍为 2,000，其中被动候选为 1,500 个 active 节点。未构造边或覆盖关系。

同一脚本提供 `--reference-normalization`：只将缓存归一化函数替换成阶段六的逐坐标实现；其余路径和参数保持相同。前后分别 10 次单请求及 10 组 2 路并发。基线和优化版本顺序执行，没有同时运行两次性能脚本。

环境：AMD Eng Sample: 100-000000954-50_Y，16 逻辑 CPU/亲和 CPU，容器 `cpu.max=max 100000`、`memory.max=max`，主机可见内存 57,420,896 KiB；Linux 6.18.18.c1126-trim、Python 3.12.13、NumPy 2.5.2。没有模拟低配设备、CPU 配额或慢磁盘；可见硬件不等于独占资源。

## 定位与变更

确定的热点是缓存 JSON 解码校验及其后重复的逐坐标 Python 归一化。排名的量级明显更小。本轮仅修改 `core/embeddings.py` 的 `_normalize_cached_vectors`：

- 缓存读取仍由 `CacheStore` 完整校验数值类型、布尔值、有限性、非零和模型维度；缓存 schema、键、TTL、容量及 LRU 不变。
- 对已经校验过的坐标用 NumPy 进行批量归一化；先按行最大绝对值缩放，仍支持极大/极小有限坐标，避免平方溢出。
- Provider 原始响应继续走原有严格校验；模型指纹前后检查、空间/节点/正文版本隔离、代及最终版本复核不变。
- 运算仍在纯 worker 中。请求取消后可放弃 worker 结果，worker 本身不会继续访问数据库或 Provider；这不意味着底层 CPU 线程可以被强行终止。

没有增加驻留向量副本或新的缓存层，没有改用有损向量、延长截止、扩大候选上限或引入向量索引。NumPy 临时数组只在这次计算中存在；本轮未测进程峰值 RSS，不对内存收益作断言。浮点计算顺序可能带来舍入级差异，参考结果一致性按数值容差验证。

## 单请求前后结果

单位 ms。nearest-rank；10 个样本的 P95 就是最大值，不能据此制定线上 SLO。

| 阶段 | 原实现 P50 | 优化后 P50 | 原实现 P95 | 优化后 P95 |
| --- | ---: | ---: | ---: | ---: |
| 热召回整体 | 812.52 | 628.06 | 830.69 | 652.59 |
| 候选快照 | 23.11 | 24.28 | 25.16 | 37.52 |
| 缓存读取总计，含解码 | 493.03 | 485.12 | 511.27 | 510.97 |
| JSON 解码及缓存校验 worker | 304.61 | 302.48 | 310.32 | 323.30 |
| LRU 更新 SQL | 16.98 | 16.68 | 18.10 | 18.01 |
| 缓存向量归一化 worker | 241.66 | 54.43 | 248.09 | 63.04 |
| 矩阵评分及排名 worker | 24.12 | 23.29 | 30.30 | 27.66 |
| 正文选择 | 0.20 | 0.21 | 0.21 | 0.24 |
| 注入前版本/状态复核 | 0.86 | 0.85 | 4.55 | 13.16 |

本次整体 P50 下降约 22.7%，P95 下降约 21.4%；不能将此比例推广到任意维度、节点数量和宿主负载。两版热召回均每轮选出 5 个完整节点，没有新增 Provider 调用。冷缓存 P95 为 42.10/43.13 ms，仍为空召回且不在前台构建节点向量。

两版均 2,011 条缓存向量，JSON 载荷完全相同，为 32,587,594 字节；优化后关闭数据库为 34,717,696 字节。文件字节数受 SQLite 页分配和随机节点 ID 影响，不将少量差异视为压缩收益。缓存主要体积及解码成本仍未解决。

## 并发和长正文边界

| 工作负载 | 样本 | P50 / P95 | 截止降级 | 实际结果 |
| --- | ---: | ---: | ---: | --- |
| 原实现，同一空间 2 路并发 | 20 | 1528.32 / 1573.34 ms | 20/20 | 空回忆，后续单请求恢复正常 |
| 优化后，同一空间 2 路并发 | 20 | 1234.17 / 1303.25 ms | 0/20 | 每次 5 节点，后续单请求恢复正常 |
| 优化后，长正文，单请求 | 3 | 664.55 / 687.17 ms | 0/3 | 0 注入节点：完整正文超预算 |
| 优化后，长正文，同一空间 4 路并发 | 12 | 1518.21 / 1708.83 ms | 12/12 | 按截止降级，后续单请求恢复正常 |

长正文使用 `--text-repeat 20`，代表节点为 1,480 字符、3,840 UTF-8 字节，整个有界快照 JSON 约 9.22 MB。每个完整节点超过默认 2,048 字节保守预算，所以单请求虽然完成向量匹配，最终不会截断正文来凑预算。这是现有整节点注入语义，不能把这里的 0 注入解释成语义检索失效。

并发测量同时每 10 ms 观测一次事件循环调度延迟。2 路并发的调度延迟 P95 从 26.14 ms 降到 17.55 ms，最大值从 239.02 ms 降到 94.90 ms。长正文 4 路时调度延迟 P95 20.73 ms、最大 117.58 ms。它只观测该进程本次调度，不能保证宿主其他任务不受影响。

`asyncio.timeout(1.5)` 是协作式截止，受事件循环调度、线程竞争和 SQLite 清理影响，实际墙钟可能超过 1.5 秒；本轮最大为 1.709 秒。请求完成后复测仍能使用数据库和 Embedding 锁，没有永久卡住，也没有补发 Provider 请求。高并发下仍可能大比例降级，不能宣传已经满足 4 路及以上并发容量。
