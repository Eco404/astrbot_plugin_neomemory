# NeoMemory 阶段一、阶段二复核记录

> 复核日期：2026-10-29（Asia/Shanghai）  
> 复核对象：阶段一身份与原始事实库、阶段二派生节点与基础记忆库

## 复核结论

阶段一和阶段二的主要目标仍然成立，可以作为阶段三抽取管线的基础。复核过程中发现四个实现问题，已在进入后续开发前修正并补充测试。

## 已修正问题

1. **Agent 身份污染逻辑用户**：原实现会把 Agent 的 `self_id` 当作普通账户，自动创建逻辑用户和账户绑定。现在只有 `actor_kind=user` 才进行逻辑用户解析和自动绑定；Agent/system/external 记录仍保留账户 ID，但 `actor_logical_user_id` 为空。
2. **同文节点更新被跳过或错误生成版本**：原实现只比较正文和 metadata 是否为空，忽略了重要性、事件时间等字段变化。现在正文不变时，重要性/元数据更新不会递增正文版本；重要性变化会重置强度，正文变化才创建新正文版本。
3. **coverage 引用不存在版本**：现在显式传入的 `atomic_content_version` 必须位于原子节点已有版本范围内。
4. **画像和人格关系跨私聊空间写入**：私聊空间的 `logical_user_id` 现在必须与空间键中的逻辑用户一致；群成员画像仍允许在群空间中指定成员逻辑用户。

## 阶段三前置事项及确认结果

以下为复核时的问题及已确认的处理结论，原复核测试计数保留为历史基线；阶段三新增测试以阶段三执行记录为准。

### 1. 人工保护是否独立于节点状态

当前 v1 用 `manual_protected` 作为节点状态，因此一个节点不能同时表达“disabled/historical”和“人工保护”。ADR-0008 的语义更接近独立的保护标志：保护正文不被自动覆盖，但节点仍可能被禁用或标记为历史。

**用户已确认，阶段三落实**：采用独立 `manual_protected` 布尔字段；旧的保护状态迁移为 `active + manual_protected=true`。禁用或标记历史不解除保护，通过独立接口人工解除，并支持可选原因。v1 事实上已经有布尔列，此次修正移除 API 状态语义并迁移旧值，不重复创建该列。

### 2. `memory.db` 的运行时接入时机

阶段二已经提供独立 `MemoryStore`，但当前插件 `main.py` 尚未在初始化时打开它，也没有把它加入健康 API。这样符合“阶段二只建基础服务”的边界，但插件运行时尚不会自动创建或报告 `memory.db`。

**用户已确认，阶段三落实**：插件初始化打开 `MemoryStore`，强制注入阶段一 `SourceStore.has_source` 作为来源存在性校验器，健康 API 增加 `memory` 状态。初始化失败/取消时清理已打开的库；关闭顺序为派生库、原始库。抽取应用层另外负责来源的空间、人格和窗口授权。

### 3. 节点版本历史查询接口

表中已保存完整 `memory_node_versions`。阶段三补齐 `list_node_versions` 公共只读接口，供人工治理和调试查看历史正文、版本号、变更类型、编辑者类型和创建时间。

### 4. 来源校验器的强制程度

没有注入 `source_exists` 时，独立存储服务仍允许 `source_record` 类型引用任意非空 ID，以兼容隔离测试；插件生产装配已强制注入真实来源校验器。外部来源使用明确的来源类型，不把“存储层可独立构造”理解为“抽取路径允许不校验来源”。

## 未发现的阻断问题

- source.db 与 memory.db 的职责边界保持一致，派生节点删除不会删除原始事实。
- 私聊和群聊空间键符合 ADR-0001；当前服务层的 generation、节点、关系和 coverage 操作不会跨空间混写。
- 阶段一在正确 `PYTHONPATH` 下的 AstrBot v4.29.3 宿主探针仍通过。直接使用 Conda 中安装的 AstrBot v4.27.2 会因旧版测试配置目录行为失败，后续统一使用开发基线源码路径。
- `write_batch_size` 在阶段一配置中明确标注为后续批量写入预留，没有把未实现功能伪装成当前能力。

两项主要设计已由用户确认，不再构成阶段三的待决策事项。人工保护迁移覆盖旧数据库、关联引用保留及重开幂等；插件装配覆盖健康信息、未知来源拒绝、初始化失败/取消和关闭顺序。完整阶段三结束后仍需按用户要求另行复核。
