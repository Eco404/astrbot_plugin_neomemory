# ADR-0019：抽取调用必须保留完整准备输入（接口提案）

- 状态：Proposed；宿主能力与接入方式待确定，当前生产尚未修复
- 日期：2026-11-02
- 关联：ADR-0004、ADR-0011、ADR-0012、ADR-0015

## 背景

抽取准备快照和input_digest约束插件提交，但AstrBot v4.29.3的OpenAI Provider在context length错误后会删减自己的上下文副本并重试。当前公开Context.llm_generate接口没有禁止该内容回退的选项，request_max_retries只限制另一层网络重试。

抽取输入把完整来源、既有记忆和画像放在一条user消息中，因此删掉这条消息不能视为允许的历史压缩。调用成功或返回合法JSON也不能证明模型看到完整准备输入。详见[宿主研究与验证](../宿主输入完整性研究.md)。

## 建议契约

1. 宿主提供明确的逐调用能力：输入不能通过删除、改写或补写业务上下文来尝试恢复。参数默认保持原聊天行为，只有插件此类结构化任务主动请求严格模式。
2. 严格模式可保留相同输入的临时网络重试，但遇到需要修改输入才能重发的条件应报错。输入完整性与实际HTTP次数上限是两项独立约束，不混为同一个开关。
3. 能力必须在Provider层明确声明并验证；不能只因Context接受`**kwargs`就假定所有Provider支持，也不能把未知参数透传给上游API。
4. 不修改共享Provider配置，不临时替换全局/实例私有方法，不把原始来源提升为system指令，不通过另建SDK客户绕过宿主Provider。
5. 输入失败不保存成功候选、不消费来源、不推进轮次。沿用失败窗口保序和维护页重新准备/重试入口，其他空间、原始采集和主聊天继续运行。
6. 配置/模型变化后的旧候选复用继续依赖现有准备摘要与凭据。引入新的调用契约时应将其版本纳入准备/任务签名，避免旧失败候选被误认作严格模式产物。

## 实施选项

| 路线 | 可交付内容 | 限制 |
| --- | --- | --- |
| 宿主公开能力 | 在隔离分支提交最小逐请求接口及测试，插件对明确支持的Provider启用 | 需要采用包含该能力的宿主版本；当前v4.29.3没有此保证 |
| 等待上游支持 | 保留当前生产路径与风险说明，后续验证稳定版再接入 | 已复现的输入回退问题继续存在，不能标记为解决 |
| 插件接管底层请求 | 自建请求或包裹宿主私有方法 | 增加凭据/重试/模型适配职责和版本耦合，本轮不推荐 |

推荐宿主公开能力路线；隔离补丁即使通过测试，也不等于已部署或上游已经接受。需单独明确支持的Provider、宿主版本，以及不支持时是明确阻止抽取还是允许带限制运行，不能静默声称已保障完整性。

## 本轮最小候选与完整契约的区别

已准备可审阅的[宿主候选补丁](../patches/astrbot-v4.29.3-no-context-truncation.patch)，逐调用参数为`allow_context_truncation`，默认True保留原聊天行为；False在现有context length错误进入删消息回退前直接抛出。能力名限定为`no_context_truncation.v1`，只应由经验证的准确Provider类型明确声明，未知子类不自动获得保证。

这只解决已复现的截断回退路径；不保证任意Provider配置覆盖、模型专用角色变换或其他输入重写都被封住，也不限制同输入网络重试次数。补丁在独立宿主副本验证，当前插件Adapter和共享AstrBot均未接入；验证和适用范围见研究记录。更广的不可变输入契约仍需逐项实现，不能直接用这个窄能力名替代。

纯插件备选是在数据消息中附带receipt并要求输出回显。它能让整条消息被删后的缺失/错误回执被拒绝，但局部删掉sources而保留receipt时仍可通过。因而它是增加协议负担的有限缓解，不是宿主发送完整性的证明；本轮未将其加入生产schema。

## 验收

采用前必须用真实Context/Provider/SDK配合模拟HTTP验证：完整输入正常提交；上下文错误不再发送删减输入；网络重试每次业务输入一致；并发严格任务与普通聊天不互相影响；截止/取消释放资源；错误候选和未持久成功窗口不被消费。OpenAI Chat、Responses及其他Provider分别声明验证范围。

本提案不增加默认LLM调用，不减弱schema/来源校验，不自动拆分已准备失败窗口。完整输入也不能保证模型保真，后续语义评估仍独立进行。
