# 抽取保真改进与协议可靠性对照

日期：2026-11-02。状态：F1～F5完成；16次真实LLM对照后v5未达采用门槛，默认仍为v3。所属：[后续开发路线](后续开发路线.md)收敛阶段 1A；结果、复核及下一步见[执行记录](抽取保真改进轮次执行记录.md)。

本轮只选择一个最小候选改进，与现有 v3 对照，并产出明确的“采用 / 保留实验 / 放弃”结论。上一轮已提供候选和落库一致性的证据，本轮复用该能力，重点进入可验证的改进。

以下保留调用前的任务框架与门槛。默认未升级，不表示v3已解决已知质量问题；下一轮转入路线1B/1C。

执行细化：本地凭据只有一个LLM条目，事前选定该模型，整轮最多16次实际请求；没有额外连通性调用。用新的薄编排脚本 `scripts/verify_fidelity_api.py` 复用既有证据/诊断和真实 `ExtractionService`，以显式固定窗口隔离模板差异，不修改旧稳定性脚本的默认行为。本轮模型对照不覆盖后台调度与抽取触发门限，恢复另用宿主/任务模拟故障测试；不是完整生产端到端验证。

两个模板从同一已关闭的基库复制，连续链各自产生前态；模型、模板、样例、基库、插件与宿主源码/SDK身份一起冻结。请求发送前持久占位，跨进程不能重新领取同一单元；发送前中断可能保守多计，不退预算。`habit_revision.node_history`仅在前窗有对应节点时适用，没有节点不要求补建，也不作为历史保真已验证的证据。

## 1. 目标、基线与边界

目标是提高被保留事实的限定完整性，减少事件摘要错误声明 full 覆盖，同时验证实验请求和失败恢复遵守既有边界。当前生产基线为 `extraction-prompt.v3` / `extraction.v2` / memory.db v7。

目标问题的依据是独立合成诊断中的候选遗漏和 full 错误，见[既有执行记录](画像漏建诊断轮次执行记录.md)。来源归属、关系视角、当前/历史与合法不保存依据既有 ADR 作为回退检查，不能用私人聊天的具体内容设计样例。

本轮保持：

- 用户画像为标签加短描述；长期节点可以记录变化历程；不是每窗都必须产生画像或节点。
- 被动召回不增加生成模型调用；抽取相关任务维持当前组合方式和资源预算。
- 严格 schema、来源/空间/版本校验、事务提交和完成凭据；非法候选不能推进来源或活动轮次。
- 失败窗口保序、人工重新准备/重试/放弃、新代成功后切换；不引入自动跳过或静默补值。
- 默认人格跳过；群聊低资源策略；原始库不自动清理。

不开展全量用户会话回放，不新增画像事实表，不安装完整第三方记忆引擎，不开展正式容量或完整宿主验收。输出协议可靠性在本轮核对请求边界并分层统计，若需原生结构化输出适配，转入路线 1C 单独对照，避免同时改变多个因素。

## 3. F1：研究、基线与独立样例

### 3.1 先用已有资料回答具体问题

复用[条件保留研究](画像条件保留轮次参考研究.md)与[选择边界研究](画像漏建诊断轮次参考研究.md)，必要时只补相关源码或论文段落：

| 资料 | 此轮核对的问题 | 采用边界 |
| --- | --- | --- |
| Graphiti | 条件/数量/时间在摘要、去重和更新中如何处理 | 不照搬图引擎或全部实体摘要目标 |
| Mem0 当前实际抽取路径 | 精确限定如何表达，追加历史和当前事实如何区分 | 当前 ADD-only 路径不是旧四操作提示词；不把变化史直接搬进画像 |
| Hermes | 持久信息、临时信息与不保存的标准 | 编码 Agent 的记忆用途不同，不直接照搬提醒频率 |
| QAFactEval / 既有来源问题审阅 | 如何同时发现输出无依据和来源限定遗漏 | 借鉴逐问题方法，不声称复现论文或额外运行在线裁判 |
| AstrBot 实际 Provider 路径 | SDK、网络重试、内容回退和任务重试的层次 | 只依赖已验证接口，不全局修改宿主共享 Provider 的重试配置 |

研究记录引用已核验版本、许可、实际路径与差异，不重复大范围检索。现有资料无法支持候选时再定向查找上游 issue/实现；不要凭项目 star 数认定质量已解决。

### 3.2 冻结评估单元

开发集共 **6 个模型窗口**，覆盖下表；一个单元可以包含多种事实，具体内容与逐问题预期在调用前冻结。

| 单元 | 窗口数 | 检查重点 |
| --- | --- | --- |
| 持久事实及后续修正 | 2，连续链 | 范围/频率/持续时间/排他限定；新增不删除其他事实；画像当前态与节点历史态 |
| 事件叙述与原子覆盖 | 2 | 完整/部分表达的边界、更新后两端版本；用已有合成节点提供稳定端点，不强制模型每次生成三层结构 |
| 说话者及主观视角 | 1 | 用户明确自述、Agent 提议/猜测、关系感受的归属；不形成无来源事实 |
| 低价值群聊/旁听 | 1 | 合法不保存、不同成员不串用、轻量画像边界 |

再预留 **2 个独立评估窗口**，改变场景和表达，核验限定与覆盖及回退维度。它们不得由私人聊天改写，也不得由本轮候选失败临时生成；不在看到候选结果后更换题目。已查看或用于设计候选的旧样例只能标为开发/回归材料。若没有人员或流程隔离，仅称“冻结评估集”，不宣称盲测。

每个窗口预先记录：来源及角色、必要旧状态、允许丢弃项、明确应保留项、允许的等价表达、禁止推断、字段对应的来源问题、依赖窗口和哈希。被测模型只看到生产协议规定的输入，不看到预期答案、评分问题或“应该通过”的提示。

连续链中两种版本从相同初态出发，各自使用自己的已提交前态，不把基线生成的结果喂给候选冒充完整链路。如果前窗结构失败，后窗标为依赖未完成；结构成功但语义失败可以继续观察影响，不因质量失败偷偷更换前态。单独验证覆盖判断时使用相同独立夹具，并与全链结果分开报告。

## 4. F2：复用证据与工程可靠性

主要工作位置：

| 模块 | 可能改动及限制 |
| --- | --- |
| `scripts/verify_stability_api.py` | 扩展显式版本、冻结清单和对照运行，不复制一套生产抽取服务 |
| `scripts/profile_quality_cases.py` | 增加独立样例与来源问题，保留旧标准和失败案例 |
| `scripts/profile_evidence.py`、`scripts/profile_candidate_diagnostics.py` | 复用候选/凭据/前后状态证据；按需补节点、关系、覆盖的必要引用，不记录无限制原始输出 |
| `core/prompts.py`、`core/extraction_apply.py` | 若候选需要显式选择模板，确保版本进入输入摘要；应用层只做必要兼容与防回退，不根据关键词修正事实 |
| `adapters/providers.py`、`core/maintenance.py` | 核对超时、取消、重试及旧候选恢复路径；无证据不修改生产策略 |
| `core/retrieval.py`、相关存储接口 | 用现有纯流程验证覆盖是否实际抑制原子，不调用真实 Embedding，也不在本轮重写召回 |
| `tests/` | 只补调用上限、版本隔离、证据完整性和关键失败路径的有效回归 |

真实评估记录放在忽略的 `data/evaluations/` 新目录，拒绝覆盖旧报告。测试使用合成数据和临时库，正确性凭据不能放 cache.db。公开输出保留错误类别、字段路径、计数和散列，不输出私人文本、凭据或完整 API 响应。

每窗至少区分：网络/Provider 失败、协议失败、应用拒绝、提交未确认、合法不保存、内容保真失败、没有非空产物可验证。候选、提交和生效内容要分开记录；非法候选不按“已形成的记忆”评分。

先用模拟网络和恢复测试验证以下路径，不以付费网络波动碰运气：

- 连接失败、限流和超时经过哪些重试层，实际总请求如何限制；取消后的任务是否继续发送请求。
- 超时发生在提交附近时先查完成凭据，不凭异常判定未提交再写一次。
- 旧合法候选重试可复用，配置/提示词/前态变化必须重新准备；非法候选普通重试不能伪装成自动修复。
- 同空间暂停、其他空间及原始采集继续；新代失败仍保留旧 active。

现有质量脚本单次最多 8 次 HTTP；本轮使用多个有清单的子运行，并建立总计账，或在保持旧默认的前提下加入等价编排。不能仅把单次上限改大后失去轮次总预算。

## 5. F3：候选选择原则

在 F1 完成后冻结候选策略。优先验证现有一次抽取内的规则组织与表达方式，例如让“保留哪些事实”和“如何压缩这些事实”边界更清楚，以及完整覆盖的保守声明标准；这里只是研究方向，不预先认定有效。

本轮只测试一个候选，使用新的版本身份（例如 v5）；不重用已撤回 v4 的版本含义。默认仍为 v3。不要同时更换模型、schema、抽取阈值、画像容量和召回参数，否则无法解释收益来源。

候选不得要求所有信息入库、每窗必有画像或事件；不得添加私人会话特定词表、正则或案例；不得通过截掉有条件的旧事实来获得更短输出。也不增加一轮生产“自我检查模型”。若最小候选不足，记录证据并在路线 1B/1C 另立实验。

若需改变 full 覆盖可信标准或新增结构化证据才能保证去重，先形成具体 ADR 提案和离线对照；这一类数据语义变更不混入提示词候选直接发布。

## 6. F4：真实调用预算与运行方法

本轮最多 **32 次实际 LLM HTTP、0 次 Embedding、0 次在线裁判调用**。这是一项待执行预算，本次写计划没有调用 API。

| 对照部分 | 窗口 | 版本 | 模型 | HTTP 上限 |
| --- | ---: | ---: | ---: | ---: |
| 开发集 | 6 | v3 + 单一候选 | 最多 2 | 24 |
| 冻结评估集 | 2 | v3 + 单一候选 | 最多 2 | 8 |
| 合计 | 8 | 2 | 2 | 32 |

使用用户已提供的模型：事前只选择一个模型时，完整矩阵上限为 16；事前选择两个模型则为 32。若执行后发现其中一个不可用，它已发出的失败请求仍计入原 32 次预算，未执行槽位不转给另一模型或用于修改候选后重试。结论只适用于实际完成的范围。若没有合格候选，只保留实际完成的基线与工程交付。

- 在请求前冻结 Provider/模型标识、提示词与schema版本、生成参数、材料/人格哈希、执行顺序、预算和隔离输出位置。使用独立合成人格，不读取真实角色卡作为本轮样例设计依据。
- 每个“模型 × 版本 × 窗口”单元最多一次实际生成请求；每次尝试包括失败请求都计账。SDK、宿主网络重试、内容回退的限制必须在隔离运行中核验，不能只依赖 SDK `max_retries=0`；无法限制时由请求计数器阻止额外发出并标记不完整。
- 初始按串行运行，避免模型并发和限流影响对照；单请求使用既有 60 秒抽取截止，总运行预算同时限制。超时不修改截止再重跑到成功。
- 无独立连通性调用额度；首个实际请求同时暴露不可用情况。未发出的请求不计，已发出的失败请求不得从预算扣除记录中消失。
- 同一模型内的两种版本使用相同来源、初始旧状态、人格和模型参数，记录执行顺序；连续链各自使用已提交前态，独立单窗夹具才要求完全相同旧状态。开发集审阅之后不能改同一候选再进入冻结评估集；候选一旦修改须另立版本和轮次。
- 预算耗尽、作用域/凭据不一致、意外生产写入或无法保证请求上限时停止相应运行。保留已有证据，不覆盖文件，不填造缺失结果。

只有人工/离线逐项审阅完成后才能给出语义结论。token、时长和实际请求数可量化；没有可信单价则不编造货币成本。一个样本的一次通过不代表消除模型随机性，重复性验证安排在后续验收矩阵。

## 7. 审阅与采用门槛

### 7.1 分层审阅

1. **工程层**：来源范围、候选解析、引用、版本、提交凭据和前后状态一致。错误时不推进来源/活动轮次，不产生部分提交。
2. **选择层**：明确应保留项是否进入合适位置；允许省略项是否被误当持久事实。无变化不天然失败，也不天然完成保真验证。
3. **内容层**：逐项核对事实主体、范围、频率、时间、排他性、否定、不确定性与当前/历史；画像描述、标签、节点、关系分别检查。
4. **覆盖层**：把事件正文与原子正文逐项比较。full 两端版本正确仍可能语义错误；再用确定性候选执行现有去重，确认最终省略了什么。

不得只从输出提出问题：遗漏的限定可能根本不在输出里。固定来源问题以外发现的新错误也计入窗口结论，保留分母、未产生项和 `uncertain`。

### 7.2 默认升级条件

候选只有同时满足下列条件才可以进入默认：

- 目标问题有实际基线差异和独立评估支持；若基线和候选均通过，不能宣称已修复或据此认定候选更好。
- 所有指定必须项通过审阅；没有新增主体错归、无依据断言、当前/历史混淆、条件/否定失真或错误 full 抑制。候选只输出空结果不能通过非空覆盖目标。
- 适用的结构、应用和恢复检查全部通过；关键依赖缺失、协议失败或无法判断不算通过。
- 在实际完成的模型范围内无已知质量回退，提示词长度、延迟和调用开销可解释；只测一个模型时明确兼容范围，并保留更广评估缺口。
- 版本切换与旧任务恢复规则经过测试；旧完成批次不重跑，旧未提交候选按已记录版本处理或明确提示重新准备。

若不满足，保留生产 v3，记录“保留实验”或“放弃”及理由。轮次工作完成不等于抽取质量门已通过；对仍开放的问题指定路线 1B/1C 的具体下一项，不在同一轮无上限增加提示词和样例。

## 8. F5：验证、复核与后续入口

按实际改动运行相关工程测试，再跑全量 pytest、Ruff、compileall、差异检查。仅文档变化不需要付费 API 或重复全量测试。静态或假模型测试不得计入真实语义质量成功数。

执行记录至少包含：研究采用/放弃依据、清单哈希、实际代码与版本、模型和调用计数、各层通过/失败/不确定/未执行、采用决定、代码与证据复核、未解决问题、下一项可执行任务。本地提交只包含代码、独立合成测试和无私人内容文档，保留用户未提交修改。

回退只影响新候选入口或默认版本；保持现有数据库、原始来源和旧完成凭据，不自动重构用户记忆。若默认未升级，不需要虚构迁移或数据回滚步骤。

本轮常规研究、隔离实验和测试无需新的产品决策。若证据要求额外生产调用、改变画像/覆盖结构、放宽 schema 或自动跳过失败窗口，先提出具体对照、成本与 ADR，再与用户讨论；本轮不自行扩大该范围。
